## 1. 프로젝트 소개와 목적

> 차곡은 소규모 정비소를 위한 예약 CRM으로, 예약 일정과 고객·차량·정비 이력을 통합 관리하고, 축적된 정비 기록을 활용해 재점검 시기가 된 고객의 재예약을 지원하는 서비스이다.

**예약 관리가 기본 기능이고, 고객·차량·정비 이력이 CRM의 기반이며, 재점검 시기 기반 재예약이 차곡의 차별점이다.** 방문 때마다 쌓인 기록으로 고객 차량의 "다음 정비할 때"를 계산해 재예약으로 잇는다. 고객은 아무것도 설치하거나 입력하지 않는다. 차곡도 고객에게 직접 문자를 보내지 않는다. 연락할 고객과 보낼 문구를 준비해 주면, 연락은 사장이 직접 한다.

| 육하원칙 | 한 줄 답 |
|---|---|
| 왜 | 소규모 정비소는 정비 기록은 남기지만 "누구에게 언제 다시 연락할지"는 사장의 기억에 맡기는 경우가 있다는 가설. 그러면 점검 시기가 된 단골이 연락 없이 정비를 미루거나 다른 곳으로 갈 수 있다 |
| 누가 | 상담 직원 없이 사장이 예약·연락까지 직접 맡는 1~5인 동네 카센터의 사장과 정비사. 정비소 개설은 서비스 관리자가 맡는다(관리 화면은 P1, 시연은 시드 계정) |
| 무엇을 | 예약 등록·조회(홈의 오늘 예약 목록, 월·주 홈 캘린더)와 예약 상세 패널, 고객·차량·정비 이력 관리. 여기에 항목별 주기 계산, 재점검 대상 목록, 방문 중 추가 점검 안내로 재예약을 잇는다. P1에서 연락 문자 초안과 연락 결과 기록 |
| 어디서 | 정비소 사무실과 현장의 웹 브라우저(PC·태블릿)에서, 정비소별로 분리된 데이터로 |
| 언제 | 방문 등록할 때, 매일 아침 오늘 연락할 고객을 볼 때, 예약을 잡을 때 |
| 어떻게 | 방문 시 주행거리와 정비 항목을 기록하면 항목별 개월 기준으로 다음 시점을 계산하고, 방문 접수 때는 주행거리를 입력하는 즉시 저장 전 미리보기로 km 기준 도래도 함께 확인 |

**목적**: "방문 기록만으로 다시 연락할 고객을 골라낼 수 있다"는 핵심 가설을, 예약 → 고객·차량 → 정비 이력 → 재점검 대상 → 재예약이 끊기지 않는 하나의 흐름으로 만들어 검증한다. 프로젝트의 우선순위는 **기능 수보다 완성도**다.

## 2. 기획 배경과 문제 정의

**문제 가설:** 전담 고객관리 인력이나 CRM 활용이 부족한 일부 1~5인 소규모 정비소에서는 예약·정비 기록이 남아 있어도 재점검 대상 선정과 후속 연락으로 이어지는 절차가 충분히 체계화되지 않았을 수 있다. 이때 사장의 기억과 수작업에 의존하는 부담이 생길 수 있다. **특정 정비소의 불편을 전체 소규모 정비소의 공통 실태로 일반화하지 않으며**, 인터뷰와 업무 시나리오 관찰로 확인할 가설이다.

### 누가 손해를 보나

- **정비소**: 점검 시기가 된 단골을 놓치면 재방문과 추가 정비 기회를 잃을 수 있다. 한번 다른 곳에 간 고객은 다시 돌아오지 않을 수 있다(가설).
- **차량 소유주**: 브레이크패드·타이어처럼 안전과 직결된 항목의 점검 시기를 모른 채 지나칠 수 있다. 문제가 커진 뒤 오면 비용도 커진다.

### 조사로 확인한 근거

- **기록과 연락이 분리되어 있다**: 정비소 문자 발송 가이드들은 고객 정보와 최근 정비 이력을 엑셀로 정리해 단체문자 서비스에 올리는 방식을 안내한다.
- **재방문 안내가 부품이 아니라 날짜 기준이다**: 마지막 정비 후 30·60·90일처럼 일괄 일수로 문자를 나눠 보내는 방식을 권장하는 안내가 있다(기존 조사, 이번에 재확인하지 않음).
- **고객 입력 방식에는 부담이 있을 수 있다**: 차주용 앱 마이클의 리뷰 한 사례에서는 주행거리 자동 연동이 장점으로, 주행거리 업데이트 오류가 불만으로 꼽힌다.
- **해외에서는 상용화되어 있다**: Tekmetric·AutoVitals는 정비 주기 알림과 후속 안내를 실제 기능으로 제공한다. 실현 가능성의 근거이며, 국내 수요 규모를 증명하지는 않는다.

따라서 방문 기록을 재점검 대상 선정·연락 준비·재예약으로 연결하는 도구가 해당 사용자군의 업무에 도움이 되는지 검증한다. 공개 서비스 자료는 기능의 존재를 보여줄 뿐, 국내 소규모 정비소의 불편 빈도나 시장 수요를 입증하지 않는다.

## 3. 시장조사와 목표 시장

팀 시장조사 문서(2026-11-23, 저장소 밖 로컬 문서)의 요약이다. 수치는 그 문서의 출처를 옮겼고 이번 정리에서 다시 확인하지 않았다. **[사실]** 외부 출처, **[가설]** 현장 검증 전 판단.

- **[사실]** 국내 자동차 누적 등록대수는 2025년 말 2,651.5만 대, 2026년 6월 말 2,667.6만 대다([국토교통부 2026-07-30](https://www.molit.go.kr/USR/NEWS/m_71/dtl.jsp?id=95092268&lcmspage=3), [KDI 경제정보센터 재게시 2026-01-29](https://eiec.kdi.re.kr/policy/materialView.do?num=276394)).
- **[해석]** 차량 유지관리 수요의 기반을 보여 주지만, 등록대수는 소프트웨어를 사는 **정비소 수**나 CRM 지불 의사를 뜻하지 않는다. 정비업체 총수·업종별 비중은 공식 원표를 재집계하지 않았고, 시장 규모 금액(TAM·SAM·SOM)은 계산하지 않는다.
- **[가설]** 초기 타깃은 예약·고객·차량·정비 기록을 적은 인원으로 관리하는 소규모 전문정비업체다.
- **지금 말할 수 없는 것**: 정비소가 새 CRM에 비용을 낼지, 차곡이 기존 제품보다 효율이 높은지, 개인정보 보호가 선택 이유가 되는지는 모두 **미검증**이다.

## 4. 주요 사용자와 사용 환경

### 대표 사용자 (기획을 위해 가정한 인물)

50대 박 사장은 정비사 1명과 함께 2인 카센터를 운영한다. 고객 대부분은 전화로 예약하거나 지나가다 들르는 동네 단골이다. 정비 내역은 장부에 꼼꼼히 남기지만, 누구에게 언제 연락할지는 기억에 의존한다. 바쁜 주에는 점검 시기가 된 단골에게 연락하지 못하고, 몇 달 뒤 그 고객이 다른 곳에서 오일을 갈았다는 이야기를 듣는다.

박 사장에게 필요한 것은 새 업무 프로그램이 아니라, 아침에 "오늘 연락할 고객"과 보낼 문구를 보여주고, 차가 들어왔을 때 "같이 봐야 할 항목"을 알려주는 화면이다. 문자는 지금처럼 자기 폰으로 보낸다. 이 인물은 조사 결과를 바탕으로 한 가정이며, 정비소 인터뷰로 검증한다.

### 서비스 사용자

| 사용자 | 하는 일 | 권한 |
|---|---|---|
| 서비스 관리자 | 정비소 워크스페이스 생성, 사장 계정 발급(아이디 직접 입력·임시 비밀번호), 사장 임시 비밀번호 재발급, 정비소 이용 정지·재개 (화면은 P1) | 정비소 목록과 운영 정보만 조회. 고객·차량·이력·예약 데이터는 조회·수정 불가 |
| 정비소 사장 | 예약 관리, 재점검 대상 확인, 고객 연락과 재방문 관리, 정비사 계정 발급·비활성화·임시 비밀번호 재발급, 서비스 이용약관 동의(정비소 대표), 정비 항목·주기 설정, 아침 알림 시간 설정, 고객·차량 비활성화·삭제와 보관 기간 경과 고객 익명화 (계정·설정 화면은 P1) | 정비사가 할 수 있는 모든 일 + 설정·계정·비활성화·삭제·파기. 우리 정비소 전체 데이터, 정비 기록 수정·예약 정정에 기간 제한 없음 (D-57) |
| 정비사 | 신규 고객·차량 등록, 예약 등록·변경·취소, 담당 지정·재배정, 방문 접수, 주행거리·정비 기록 입력, 추가 점검 항목 확인, 자기 비밀번호 변경 | 설정(정비사 계정·항목 기준표·알림 시간)과 비활성화·삭제·파기를 뺀 모든 업무. 정비 기록 수정·예약 정정은 본인 담당만, 3일 이내 (D-57). 약관 필수 동의 없음 |
| 차량 소유주 | 간접 수혜자. 계정이나 앱 설치 없이, 사장이 보내는 정비 이력 기반 안내를 받음 | 없음 |

서비스 관리자의 원칙은 한 줄이다: **정비소를 열고 닫을 수 있지만, 정비소 안을 들여다볼 수는 없다.** 관리 대상은 고객과 그 차량이며, 신규 고객은 첫 방문 때 현장에서 등록하거나 전화 예약 때 확인한 정보로 미리 등록한다. 고객 1명이 차량 여러 대를 가질 수 있다. 계정은 한 사람이 하나씩 쓰고 공유하지 않으며, 사장이 직접 정비하면 사장 계정이 담당 정비사가 될 수 있다.

### 사용 공간과 시점

- **정비소 사무실 PC**: 사장이 예약, 재점검 대상 목록, 고객 연락을 처리한다. 문자 초안은 복사해 사장 폰으로 보낸다.
- **정비 현장 태블릿**: 정비사가 차량 앞에서 방문 등록과 이력 입력, 추가 점검 안내를 확인한다.
- **서비스 관리자 화면(PC)**: 정비소 개설과 상태 관리만 한다. 정비소 화면과 주소·메뉴가 분리된다.

모두 설치 없이 웹 브라우저로 쓰며, 화면은 PC와 태블릿 크기에 맞춘다.

| 시점 | 누가 | 하는 일 |
|---|---|---|
| 정비소 도입 시 (1회, P1) | 서비스 관리자 → 사장 → 정비사 | 정비소 생성·사장 발급 → 사장 첫 로그인(비밀번호 변경·약관 동의) → 정비사 발급 → 정비사 첫 로그인(비밀번호 변경) |
| 매일 아침 영업 전 | 사장 | 홈에서 오늘 예약과 "오늘 연락할 고객 N명"을 보고, 연락할 고객을 고름. P1에서는 사장이 고른 시간에 브라우저 알림, 문자 초안을 복사해 직접 보내고 결과 기록 |
| 전화 예약을 받을 때 | 사장 | 신규 고객이면 확인한 정보로 등록하고 예약을 잡음. 그 차량의 점검 시기 항목을 미리 확인 |
| 차량이 입고될 때 | 정비사 | 방문 접수(예약이 있으면 진행중으로), 주행거리 입력, 미리보기로 추가 점검 안내 확인 |
| 정비가 끝났을 때 | 정비사 | 수행 항목, 거절된 항목, 외부 정비 여부 기록 |

### 데이터가 머무는 범위

- 모든 고객·차량·이력·예약 데이터는 정비소 단위로 분리된다. 로그인한 정비소의 데이터만 보인다.
- 다른 정비소의 데이터를 요청하면 **404 "없음"**으로 답한다. 거부(403)로 답하면 그 데이터가 있다는 사실이 드러나기 때문이다.
- 서비스 관리자 계정은 별도 표(`platform_admin`)에 두고 토큰에 정비소 정보가 없어 정비소 데이터를 조회할 기준이 없다. 반대로 사장·정비사 토큰으로는 서비스 관리자 API를 쓸 수 없다(403, D-63 B10 — 이미 구현됨).
- 고객 정보는 주기 계산과 연락에 필요한 최소한만 받는다. 주민번호, 주소 등은 받지 않는다. 목록 화면의 연락처는 서버가 가린다(P0-나머지, 상세 화면과 문자 초안은 전체 번호).
- 이 원칙은 "서비스 기능(화면·API)으로는 정비소 데이터에 접근할 수 없다"는 뜻이다. 서버나 DB에 직접 접속하는 개발·운영자의 접근은 MVP 범위에서 다루지 않는다.

## 5. 핵심 기능 및 업무 흐름

### 시나리오 A. 재점검 알림 (정비소가 먼저 연락)

1. A 고객 차량은 2년 전 정기 점검을 받았다.
2. 시스템이 항목별 다음 정비 시점을 계산한다.
3. 재점검 시기가 된 차량이 "재점검 대상" 목록에 뜨고, 홈에는 "오늘 연락할 고객 N명"으로 요약된다. 이미 예약이 잡힌 차량도 목록에 남고 "예약 있음"으로 표시되어 중복 연락을 피한다.
4. 사장이 고객에게 연락해 예약을 잡는다. 이미 다른 곳에서 했다고 하면 외부 정비로 기록하고 주기를 다시 시작한다(P0-나머지).
5. (P1) 사장은 목록에서 문자 초안을 복사해 자기 폰으로 보내고, 연락 결과를 기록한다.

### 시나리오 B. 추가 정비 권유 (방문 중 안내)

1. B 고객이 6개월 만에 엔진오일 교체로 방문한다.
2. 정비사가 방문을 등록하고 주행거리를 입력하면, 저장하기 전에 미리보기로 차량의 전체 항목 상태가 뜬다.
3. 브레이크패드 점검 후 1년이 지나 "점검할 때"로 표시된다. 개월로는 여유인 항목도 입력한 주행거리가 기준 km 이상이면 "도래"로 표시된다.
4. 정비사가 권유한다. 교체하면 이력에 남고 주기가 다시 시작된다. 거절하면 거절로 기록하고(P0-나머지) 주기는 그대로 유지되어, 다음 재점검 목록과 다음 방문 미리보기에 "지난 방문 거절"과 함께 다시 나타난다.

### 신규 고객 간편 등록

1. 정비사나 사장이 차량번호나 연락처로 조회해 신규 여부를 확인한다.
2. 신규면 고객명·연락처·차량번호·차종만으로 등록한다(D-58). 현장 방문 때뿐 아니라 전화 예약 때 확인한 정보로도 등록할 수 있다. 연식·주행거리는 확인 가능할 때 추가하고, 비어 있으면 정비 시작(방문 접수) 때 입력한다.
3. 안내 수신 동의 체크박스는 기본이 체크 안 됨이다. 고객에게 물어보고 동의한 경우에만 체크한다. 동의하지 않은 고객은 재점검 대상 목록에 뜨지 않는다.
4. 기존 고객의 새 차량이면 고객을 새로 만들지 않고 차량만 추가한다.
5. 방문을 접수하고, 정비가 끝나면 다음 점검 시기를 계산한다.

### 정비소 시작 흐름 (P1, D-60·D-61)

1. 정비소 사장이 이용을 신청한다(전화·문의 등, 신청 접수 화면은 P2).
2. 서비스 관리자가 정비소를 생성하며 사장 아이디와 임시 비밀번호를 직접 정해 발급하고, 별도 채널로 사장에게 전달한다.
3. 사장이 임시 비밀번호로 로그인 → 새 비밀번호 설정 → 서비스 이용약관 필수 동의(개인정보 처리방침은 고지) → 홈.
4. 사장이 정비사 계정을 발급하고 임시 비밀번호를 직접 전달한다. 정비사는 첫 로그인에서 새 비밀번호를 정한 뒤 CRM을 쓴다(약관 단계 없음).
5. 중간에 창을 닫아도 다시 로그인하면 남은 단계부터 이어진다. 화면 주소를 직접 입력해도 서버가 막는다.
6. 이후 서비스 관리자는 정비소 목록에서 상태(이용 중 / 정지)만 관리한다. 정비소 내부 데이터는 보지 않는다.

P0 시연에서는 관리 화면 없이 시연 DB의 시드 정비소·시연 계정(비밀번호 1234, D-44)으로 시작한다. 시연 데이터는 시연 전용 DB에만 넣고 서버가 자동으로 넣지 않는다(D-43). 계정 규칙의 자세한 값(아이디 6~20자, 비밀번호 8~20자 영문·숫자·특수문자 등)은 상세 기획안 04장.

### 예약과 정비 기록 운영 (요약)

- **예약 상태**: 예약 → 진행중(방문 접수) → 방문 완료. 예약·진행중 → 취소. 노쇼는 시각이 지난 "예약"에서만. 시각이 지났는데 "예약"이면 "처리 필요"로 표시한다.
- **담당 정비사**: 같은 담당·같은 시작 시각의 유효 예약은 막고, 같은 시각 다른 담당은 허용한다(D-51).
- **지난 예약 정정·재배정**: 지난 예약과 끝난 예약은 상태·메모만 정정하고, 정정·재배정은 모두 이력에 남는다(D-53).
- **정비 기록 수정**: 수정은 되고 삭제는 없으며, 수정자·날짜·수정 전 값을 이력으로 남긴다(D-55).
- **고객·차량 정리(P1)**: 이력 없는 고객은 삭제, 있으면 비활성화. 5년 경과 고객 익명화는 법적 검토 뒤 구현한다(D-56·D-64).

세부 규칙과 권한은 상세 기획안 06·07장.

### 연락 지원 흐름 (P1)

차곡은 문자를 보내지 않는다. 누구에게 무엇을 보낼지까지 준비한다.

1. 사장이 정한 시간에 브라우저 알림 "오늘 연락할 고객 N명"이 뜬다(차곡 탭이 열려 있을 때, 설정은 브라우저에 저장). 탭이 닫혀 있으면 홈 요약이 기본 경로다.
2. 재점검 대상 목록에서 고객마다 정보성 안내 문자 초안이 만들어진다. 한 고객의 여러 차량·항목은 한 문자로 묶는다.
3. PC에서는 "복사"로, 폰·태블릿에서는 "문자 앱 열기"로 번호와 본문을 채워 넘긴다. 보내는 것은 사장의 폰이다.
4. 사장이 연락 결과(예약함, 부재, 이미 정비함, 연락함, 번호 오류, 연락 거부)를 직접 기록한다. 기록된 고객은 목록에 "연락함(날짜)" 꼬리표가 30일 표시된다. "연락 거부"를 고르면 동의를 해제할지 묻는 확인 대화상자가 뜬다.

### 주기 계산 규칙

| 항목 | 개월 | km |
|---|---|---|
| 엔진오일 | 6 | 10,000 |
| 에어클리너 | 12 | 15,000 |
| 에어컨필터 | 6 | 10,000 |
| 브레이크패드 | 12 | 20,000 |
| 타이어 상태 점검 | 6 | 10,000 |
| 배터리 | 36 | 60,000 |

- 날짜 판정(재점검 대상 목록)은 개월 기준만 쓴다: 마지막 기록일 + 설정 개월 = 다음 정비 시점. 임박은 달력상 1개월 이내, 도래는 기준과 같아도 도래(≥)다.
- 방문 접수 때 입력한 주행거리가 "마지막 기록의 km + 주기 km" 이상이면 개월과 상관없이 도래다. 미리보기는 기록을 남기지 않는다.
- 실제 교체(수행)와 외부 정비만 주기를 다시 시작한다. 점검·거절·점검 결과(양호/주의)는 주기를 바꾸지 않는다.
- 근거가 없으면 "미확인". 상태는 "미확인 / 여유 / 임박 / 도래" 네 단계이고 저장하지 않고 볼 때마다 계산한다.
- km를 날짜로 환산하는 월평균 주행거리 추정(기록 2회 이상)은 P1 1순위다. 그전까지 km만 넘은 차량은 방문 전 대상 목록에 뜨지 않는다.
- 표시되는 항목은 차량 상태 진단이 아니라 "확인이 필요한 항목"이다.

### 데이터와 기술 (요약)

V1 9개 테이블(적용됨)에 P0-나머지(V2) 이력 표 2개, P1(V3) 연락 기록·칼럼 추가가 더해진다. `platform_admin`을 제외한 모든 테이블은 정비소 기준으로 나뉘고, 핵심 부모·자식 관계는 DB 복합 FK로 한 번 더 막는다. 약관 동의 기록 표는 P1 초안이며 DB 담당자 검토 전이다. 테이블별 내용은 상세 기획안 10장.

| 구분 | 결정 |
|---|---|
| 프론트 | React + Vite, JavaScript 위주 + TypeScript 병행 |
| 백엔드 | Java 21 + Spring Boot, REST API, 공통 응답과 전역 예외 처리 |
| DB | MySQL 8 + JPA, Flyway (변경마다 버전 파일, V1은 P0-핵심·V2는 P0-나머지·V3는 P1) |
| 인증 | JWT. 서비스 관리자 토큰에는 정비소 정보가 없음. P1부터 요청마다 계정 상태(비활성·비밀번호 변경·약관)를 서버가 확인 |
| 홈 캘린더 | 직접 구현 (월·주 보기, 일 보기 없음, P0-나머지) |
| 비밀값 | Git에서 제외 (DB 비밀번호, JWT 키, 운영 계정 비밀번호) |

주기 계산은 서버의 한 곳(cycle)에서만 하고, 차량 상세·방문 접수 미리보기·재점검 대상 목록·문자 초안이 같은 결과를 쓴다.

## 6. 유사서비스 비교 핵심 발견

국내외 20개 후보 중 정비소 내부 업무와 가장 직접 비교되는 11개를 상세 비교했다(본문 7개 + 상세 4개). 공개 자료 조사이며 2026-11-24 현재 기능·가격·관리자 화면을 새로 실측하지 않았다. 상세는 [`RESEARCH_유사서비스_사용자후기.md`](RESEARCH_유사서비스_사용자후기.md), 20개 원문은 [`RESEARCH_유사서비스_20개_2026-11-23.md`](RESEARCH_유사서비스_20개_2026-11-23.md).

| 서비스 | 주 이용 대상 | 조사 자료에 나타난 비교 영역 | 차곡에서 참고한 설계 선택 |
|---|---|---|---|
| 마이클 | 차량 소유주 | 차량 관리·정비 시기 안내·예약 접점 | 고객용 앱 없이 정비소 직원이 기록하는 흐름 |
| 마이클 파트너스 | 입점 정비소 | 플랫폼 예약·파트너 운영 | 플랫폼 유입과 별개인 전화·현장 고객 기록을 우선 |
| 정비마법사 | 정비업체 | 고객·정비 이력·교환주기·업무 관리 | 종합 운영보다 예약·이력·재점검 CRM 경로에 집중 |
| AutoVitals | 정비업체 | 디지털 점검·후속 안내·고객 관리 | 점검 시기 안내와 연락 준비의 연결 |
| Tekmetric | 정비업체 | 예약 캘린더·정비 관리·CRM | 예약 상세에서 이력 확인, 재점검에서 예약 등록 |
| 오토케어 | 정비소·차량 소유주 | 정비 이력·예약·정비 예정 알림 | 이미 있는 주기 안내 기능을 독창성으로 주장하지 않음 |
| 카호스 | 정비업체 | 접수 → 진행 → 완료 → 출고, 예약·이력 | 예약 → 진행중 → 방문 완료의 최소 상태 흐름 |

상세 분석에 더한 4개(카메이트·카포스 차량관리·AutoLeap·Shopmonkey)는 차량번호 선조회 등록, 기록·주기 계산 집중, 자동 발송 대신 문자 초안, 홈 예약 목록·캘린더·패널 구성의 근거로 썼다.

**핵심 발견**

1. **예약·정비 이력·주기 알림·재방문 CRM은 이미 여러 제품에 있다.** 차곡은 기능의 독창성이나 우월성을 주장하지 않는다.
2. **실제 정비소 업무에서 시간과 노력이 드는 단계**가 비교의 초점이다. 해외 공개 후기 8건의 요지에서는 통합 조회·고객 소통의 편리함과 함께 기본 업무 탐색, 기기 사이 재입력, 신규 직원 학습, 비용, 연락의 수작업 부담이 언급됐다. 단, **8건 모두 2026-11-24 원문 재확인을 시도했으나 자동 접근이 막혀 확인하지 못했다.** 검증된 후기로 쓰지 않고 검증 질문의 출발점으로만 쓴다.
3. **국내 근거는 비어 있다.** 국내 서비스의 정비소 운영자 후기는 독립적으로 확인하지 못했고(카호스 포털의 차주 후기는 정비소의 프로그램 사용 후기가 아님), 국내 1~5인 정비소 인터뷰·관찰은 **미실시**다.
4. 이 조사는 기능·정책·범위를 바꾸는 근거로 쓰지 않는다.

## 7. 차별화 방향과 한계

차곡은 **1~5인 독립 정비소의 전화·현장 예약부터 고객·차량 조회, 정비 기록, 재점검 대상 선정, 연락 준비와 재예약까지** 연결하는 B2B 예약 CRM을 개발하고자 한다. 차별화는 기능 독점이 아니라 **정해진 사용자군에서 필요한 흐름에 집중하는 구현 선택**이며, 검증할 가설이다.

| 설계 선택 | 정확한 의미 | 한계 |
|---|---|---|
| **고객 앱 없는 운영** | 고객은 설치·가입·입력을 하지 않고, 정비소 직원이 방문·전화 때 기록한다. 차주용 서비스와 사용 접점이 다르다는 뜻 | 모든 정비소용 프로그램에 없는 독점 기능이 아니다. 정비소가 기록하지 않으면 이력이 비고, 고객이 다른 곳에서 정비하면 빈틈이 생긴다(외부 정비·거절 기록과 "미확인"으로 보완) |
| **사장의 수동 연락** | 서비스는 대상·문자 초안·연락 결과 기록을 지원하고, 발송은 사장의 폰에서 사장이 한다. 발송 대행 비용·책임을 서비스가 지지 않는다 | 발송과 결과 기록의 수작업 부담은 남는다. 이 부담이 실제로 받아들여지는지는 인터뷰로 확인한다. "문자 앱 열기"는 기기마다 확인이 필요하다 |
| **정비소별 데이터 격리** | 모든 데이터가 정비소 단위로 나뉘고, 다른 정비소 데이터는 404, 서비스 관리자는 정비소 안을 볼 수 없다 | 경쟁 우위가 아니라 반드시 지킬 보안 원칙이다. 서비스 기능(화면·API) 수준의 통제이며, 서버·DB 직접 접근은 MVP 밖이다. 경쟁 제품의 격리 정책은 비교하지 않았다 |
| **초기 이력의 불완전함을 드러냄** | 근거가 없으면 "미확인", 외부·거절 기록 활용 | 경쟁사가 이를 처리하지 못한다고 단정하지 않는다 |
| **방문 중 주행거리 미리보기** | 방문 접수 화면에서 저장 전에 점검 시기 정보를 확인 | 예약 상세 패널은 기존 정보의 요약만 보여 준다 |

### 알고 있는 한계

- P0에서는 재점검 대상 목록이 개월 기준으로만 판정된다. 주행거리가 많은 차량은 방문 전에 놓칠 수 있으며, P1 1순위인 월평균 추정으로 보완한다.
- 사장 아침 알림(P1)은 차곡 탭이 열려 있을 때만 동작하고, 설정은 브라우저에 저장되어 다른 기기와 공유되지 않는다. 탭을 닫아도 오는 알림은 P2 웹 푸시다.
- **소유주 변경은 MVP에서 다루지 않는다.** 차량의 소유주가 바뀌면 사장이 새 고객으로 등록한다.
- **개인정보 보관의 법적 근거는 아직 검토 중이다.** 담당 PM이 F-CUS-10·11 구현 이슈 전, 그리고 실제 고객정보를 다루기 전에 처리 근거·보관 기간·파기·업무위탁 관계를 검토한다(D-64). 그전에는 관련 기능을 완료나 운영 적합으로 표시하지 않고, 시연은 가상 데이터만 쓴다. 이 문서는 법률 검토를 대신하지 않는다.
- **이용약관·개인정보 처리방침 전문은 법률 검토 전 최종 확정하지 않는다.** P1에서는 화면·API·기록 구조만 만든다(D-61).
- 정비 기록은 수정만 가능하고, 통째로 무효 처리하는 기능은 P2다. 지난 예약 정정은 상태·메모에 한정되고 정정해도 정비 기록은 자동으로 만들어지지 않는다.
- JWT는 토큰이 만료될 때까지 유효하다. 예외는 P1의 비활성 정비사(이미 받은 토큰도 차단, D-62)와 비밀번호 변경·약관 동의 전 제한 상태다. 로그아웃은 화면에서 토큰을 지우는 방식이며, 서버의 강제 로그아웃과 정지 정비소 토큰 즉시 차단은 P2다.
- 캘린더 직접 구현은 부담이 큰 결정이라 월·주 보기 모두 P0-나머지에 둔다. P0-핵심은 홈의 오늘 예약 목록과 예약 상세 패널로 순환을 완성한다.
- 점검 주기 상태와 점검 결과(양호/주의)는 점검 시기 안내·관찰 기록이지 부품 상태 진단이 아니다. 정상·불량처럼 단정하지 않고, 점검하지 않은 항목을 양호로 추정하지 않는다.
- 백엔드·프론트 레포가 나뉘어 있어 API 명세와 실제 응답이 어긋날 수 있다. 명세는 `chagok-docs` 한 곳에만 두고 연결 때마다 대조한다.
- 유사 서비스 비교는 공개 자료에 기반했고, 사용자 후기는 원문 재확인 전이며, 실제 정비소 인터뷰와 경쟁 제품 화면 검증은 하지 않았다.

## 9. 확정된 개발 범위

### 단계를 나누는 기준

"정비사에게 필요한 모든 기능인가?"보다 **"예약과 고객 관계 관리의 업무 흐름을 개선하는가?"**를 먼저 묻는다.

| 단계 | 기준 | 이번 프로젝트에서 |
|---|---|---|
| P0 | "방문 기록만으로 다시 연락할 고객을 골라낼 수 있다"는 핵심 가설을 끝까지 검증하는 최소 루프. 시나리오 A·B가 P1 없이 끝나야 한다 | MVP. P0-핵심 → M2 통합 검증 → P0-나머지 순서 |
| P1 | 같은 가설의 정확도와 운영 편의를 높이는 기능. 없어도 시나리오는 끝나지만, 있으면 더 정확하거나 손이 덜 간다 | MVP. P0 다음 순서로 모두 구현하고 M3 MVP 검증에서 확인 |
| P2 | 새 가설, 새 사용자 접점, 외부 연동이 들어가는 확장 | M3 MVP 검증 통과 후 `결정` 이슈로 골라 추가. 그전에는 문서로만 두고 코드·테이블·화면을 만들지 않음 |
| Non-goal | 차곡의 방향과 맞지 않아 하지 않기로 한 것 | 만들지 않고, 확장 방향으로도 소개하지 않음 |

**MVP = P0-핵심 + P0-나머지 + P1.** 완성도와 테스트가 확인된 MVP 위에서만 P2를 더한다.

### MVP 기능 (P0 · P1)

| 단계 | 기능 | 설명 |
|---|---|---|
| P0-핵심 | 로그인·정비소별 데이터 격리 | 시드 계정 JWT 로그인, 사장·정비사 역할, 모든 데이터에 정비소 구분. 서비스 관리자 계정은 별도 표, 시드 서비스 관리자로 "고객 목록 접근 거부"를 확인하고, 반대로 사장·정비사 토큰의 관리자 API 호출은 403(B10, 구현됨) |

### P2 — 확장 계획 (M3 MVP 검증 후 추가 후보)

- **A. 재방문 축 강화 (우선순위 1)**: 연락 대상 유형 확장(거절 후속·장기 미방문·방문 후 안부), 문자 템플릿 관리, 탭을 닫아도 오는 웹 푸시, 운영 리포트(재방문율·연락 → 예약 전환율·권유 수락률). 고객 발송은 여전히 하지 않는다.
- **B. 기반 정비 (우선순위 2)**: 방문 테이블 분리·정비 기록 무효 처리, 예약 고도화(영업시간·수용량·근무 시간표·노쇼 관리·동시 요청 잠금·드래그·반복 예약), 6개 항목 밖 상세 점검·도면 입력, 강제 로그아웃·정지 즉시 차단·일반 접근 감사 로그, 동의·철회 이력.
- **C. 사업 확장 (우선순위 3)**: 고객 확인 링크(조회 전용), 정비소 셀프 온보딩(이용 신청·승인·요금제), 차량번호 기반 차종 조회.

> 발표용 한 줄: 지금은 사장이 목록을 보고 직접 연락하지만, 다음 단계에서는 연락할 이유를 넓히고(거절 후속·장기 미방문), 그 효과를 숫자로 본다(재방문율·전환율).

### Non-goal — 하지 않을 것

| 항목 | 하지 않는 이유 |
|---|---|
| 서비스가 고객에게 직접 문자·카카오톡·이메일 발송 | 정비소가 고객과 직접 연락하는 관계를 돕는 것이 방향. 발송 대행 비용과 발송 책임을 서비스가 지지 않음 |
| 결제·정산, 부품 재고 | 종합 업무 프로그램과 경쟁하지 않고 CRM에 집중 |
| 고객용 앱·가입·로그인 | "고객 입력 없음"이 차별점 |
| 정비소 간 공동 이력 | 목표는 완전한 차량 이력이 아니라 "우리 정비소의 고객 관계" |
| 마케팅 캠페인·세그먼트 빌더 | 재방문 안내가 축. 홍보 도구로 넓히지 않음 |

계정·온보딩을 P1로 정하면서 **만들지 않기로 한 것**: 정비소·고객 셀프 회원가입(정비소 셀프 온보딩은 P2 C 묶음), 소셜 로그인, 이메일·SMS 인증과 자동 발송, 약관 버전 관리 화면·정기 재동의, 필요 이상의 감사·보안 체계, 역할 변경·직원 소속 이동·계정 삭제(D-60~D-62).

아직 차례가 오지 않은 단계의 기능과 Non-goal 기능은 빈 화면, 연결되지 않은 버튼, 쓰지 않는 API나 테이블로 미리 만들지 않는다. 단, 정비 구분값 4개처럼 "값은 처음부터"로 정한 것과 담당 정비사 칼럼(D-51)은 예외다.

### 완성도 원칙

- 기능 수보다 시나리오 A·B가 끝까지 막힘없이 시연되는 것을 우선한다.
- **완료의 정의**: 기능 하나는 화면, API, 시드 데이터, 백엔드·프론트 `develop` 통합 실행이 모두 갖춰져야 완료로 센다. 주기 계산·정비소 격리·계정 상태에 닿는 기능은 해당 테스트 통과까지 포함한다. 바뀐 명세가 `chagok-docs`에 반영되어야 완료다. 하나라도 빠지면 미완료이며, M4 기능 동결 이후 시연에 넣지 않는다.
- 발표용 시연 데이터(고객 10명 내외, 다양한 이력)를 미리 준비한다. 시연 정비소는 2곳 이상 만들어 데이터 격리를 보여준다.
- 서비스 관리자로 로그인해 고객 목록에 접근하면 거부되는 장면을 시연에 넣는다.
