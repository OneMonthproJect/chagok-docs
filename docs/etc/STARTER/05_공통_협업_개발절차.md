## 2. 한 이슈의 흐름

```
이슈 확인 → develop 동기화 → 개인 브랜치 → (AI면 계획 승인) → 구현 + 테스트 → 로컬 검증
→ PR(develop) → CI ✅ → 팀원 확인(두 레포 함께 띄워 실행) → done-verified → Squash merge
→ issue-close가 이슈 닫음 → (기능 묶음) 통합 검증 → 마일스톤 때 develop → main 릴리스
```

|---|---|---|---|

## 3. CodeRabbit (조건부)

| 대상 | 방식 |
|---|---|
| 릴리스 PR (backend·frontend develop → main) | `release` 라벨로 자동 1회. 안 돌면 `@coderabbitai full review` 댓글 |
| 중요 develop PR (`review-me` 라벨: backend cycle·global·마이그레이션, frontend `src/app`·`src/shared/api`) | 필요할 때 `@coderabbitai review` |
| docs PR | 대상 아님 |

현재까지 CodeRabbit 리뷰 기록은 **없다**(backend #16·frontend #13·과거 릴리스 PR). App 설치·동작 여부는 다음 코드 릴리스 PR에서 확인한다. 코드 레포 `review-me`·L3 PR은 CodeRabbit 「필요」로 본다(D-66 ④, 확정). CodeRabbit 리뷰는 머지 차단 조건이 아니고, 리뷰가 없으면 "미실시"로 적는다.

이 예외는 #77 작업 종료와 함께 끝난다.

## 5. 지키는 것

- `main`·`develop` 직접 push, force push, 이력 재작성 금지.
- P0-핵심 범위 밖(취소·노쇼·월·주 캘린더·담당 정비사 입력·진행중·정정·마스킹)을 미리 만들지 않는다. 홈은 날짜별 오늘 예약 목록.
- 인증은 지금 **JWT 검증만** 있다. 로그인·토큰 발급은 12 4장 2번 이슈에서 만든다.
- 공용 DB 직접 수정 금지. 마이그레이션은 새 V 번호로만(머지된 V1 수정 금지), DB관리 리뷰.
- 범위 추가 의견은 `결정` 이슈 + 전원 합의가 먼저(CONTRIBUTING 3장).
- 기능 `develop` 머지와 `main` 릴리스를 혼동하지 않는다.

## 6. D-71 적용 안내 (병렬 개발 단계, 2026-11-24 팀 회의 확정, chagok-docs#109)

| 항목 | 안내 |
|---|---|
| 적용 시점 | docs·backend·frontend의 D-71 PR(chagok-docs#109 연결)이 각 레포 develop에 머지된 뒤부터. 그 전에는 pr-check가 `Refs`만 있는 본문을 ❌로 표시한다 |
| 최신 develop 받기 | 진행 중인 브랜치는 그대로 둔다. 새 PR은 `git switch develop && git pull --ff-only origin develop`에서 새 브랜치로. 진행 중인 브랜치에 develop이 필요하면 `git merge origin/develop`(rebase·reset·force push 하지 않음) |
| 작업 보호 | 미커밋 변경이 있으면 먼저 커밋하거나 `git worktree add`로 다른 폴더에서 작업한다. 일괄 pull·reset·rebase·브랜치 삭제를 하지 않는다 |
| 스킬·에이전트 | 형상관리자의 릴리스·배포 공지 뒤 작업 폴더에서 `bash chagok-docs/scripts/update-workspace.sh`(chagok-docs#208, [03](03_공통_클론_개발환경.md) 3장). claude.ai 사용자는 형상관리자가 재배포한 `.skill`로 덮어쓴다 |
| Closes / Refs | 이슈 **전체** 완료 조건을 채운 최종 PR = `Closes #n` + `done-verified`. 일부만 끝냈고 혼자 머지할 수 있으면 `Refs #n`(머지 후 이슈 열림, 라벨 없음). 같은 이슈의 다음 PR은 새 브랜치에서. 최종 PR에는 앞선 `Refs` PR 링크와 검증 근거를 적는다 |
| Draft | PR 자체가 미완·리뷰 준비 전·필수 의존성 미충족일 때만. 이슈 전체가 미완이라는 이유만으로 Draft로 두지 않는다 |
| 이미 열린 PR | 바꿀 필요가 있을 때만 작성자가 직접 고친다. 이슈 일부만 끝내는데 `Closes`로 올린 PR은 본문 첫 줄을 `Refs #n`으로 바꾼다(`done-verified`를 붙이기 전에). 그 밖의 PR은 그대로 둔다. 머지된 PR·닫힌 이슈는 고치지 않는다 |
| PR Assignee | 기본 비움. 인수인계·담당 변경 때만 지정 |
| 릴리스 요청 | `main` 반영은 형상관리자(dyk816)가 마일스톤 검증 후 한다. 먼저 반영할 확정 문서·규칙·필수 변경이 있으면 대상 레포·PR·이유·검증 근거를 이슈·PR 댓글로 형상관리자에게 요청한다. `main` ↔ `develop` 차이는 정상이다 |

## 7. 검증 재사용 · 사후 리뷰 · 막혀도 계속하기 (chagok-docs#208)

규칙은 원본만 본다 — 여기에 다시 적지 않는다.

- **검증 재사용·영향 범위·자기 검증·사후 리뷰**: CONTRIBUTING 5장 「검증 근거와 사후 리뷰」·「검증 재사용」(D-66·D-71), AI 작업은 `ai-rules.md` 「검증 재사용」. 작업 등급별 필수 검증·CI·`pr-reviewer`·팀원 확인·통합 검증은 그대로다.
- **기록**: PR 본문·댓글에 「실행」·「재사용」·「미검증」을 나눠 적는다(GUIDE 22장 표기). 별도 검증 문서는 만들지 않는다.
- **막혔을 때**: 승인 없이 범위를 넓히지 않고, 규칙 충돌·문서에 없는 결정은 우회하지 않고 보고한다(`ai-rules.md` 「작업 절차」). 안전 권장(정책 아님): 같은 명령을 바로 되풀이하지 말고 원인부터 보고, 막힌 일만 멈추고 독립적인 나머지는 계속한다.
