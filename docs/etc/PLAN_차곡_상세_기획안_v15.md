## 설계 원칙

예약 CRM을 기본으로 두고 정비 주기 기반 재방문 흐름에 집중하며, 데이터 보호는 가볍게, 완성도 있게 끝낸다. 이 문서는 `chagok-docs`의 기준 문서(00 PRD·04 기능명세서·07 ERD·08 API, 2026-11-23 `develop`)에 맞춘 v14 정책을 보존하고 조사·비교·검증 표현을 보완한 v15이다. v9에서 2026-11-22 팀 회의 확정 5건을, v10에서 문서 작성 전 결정 5건(점검 결과, 외부·거절 단계, 예약 목적, 홈, 차량 도면)을, v13에서 2026-11-23 회의 결정(D-50~D-59: 마일스톤 이름, 담당 정비사, 진행중, 지난 예약 정정, 홈 캘린더, 정비 기록 수정, 삭제·보관, 역할 개정, 필수 입력, P1 미결 확정)을 반영했다. 2026-11-24 정리에서 같은 날 두 번째 회의 결정(D-60~D-65: 계정 발급·첫 로그인·약관 동의·비활성 정비사 토큰(P1), 세부 정책 B01~B12, POL-46 검토 담당·기한, Git 사전 준비 예외)을 04·04A·04B·10·12·14장에 반영했다. **정책을 새로 고른 것은 없다.** 문서와 이 기획안이 다르면 `chagok-docs`의 문서가 맞다.

- **예약 CRM이 기본, 재방문 흐름에 집중**: 예약 → 고객·차량 → 정비 이력 → 재점검 대상 → 재예약이 끊기지 않는 것이 기본이다. 주기 계산·재점검 대상·방문 중 안내를 소규모 정비소의 업무 흐름에 연결하는 것이 검증할 가치다.
- **판단 원칙**: "정비사에게 필요한 모든 기능인가?"보다 "예약과 고객 관계 관리의 업무 흐름을 개선하는가?"를 먼저 묻는다.
- **단계는 가설로 나눈다**: P0는 핵심 가설을 검증하는 최소 루프, P1은 정확도와 운영 편의, P2는 새 가설·새 접점·외부 연동, Non-goal은 하지 않을 것이다.
- **MVP = P0 + P1**: P1까지 모두 만들어 완료 정의와 테스트를 통과한 것이 MVP다. P2는 M3 MVP 검증을 통과한 뒤에만 `결정` 이슈로 하나씩 더한다.
- **순서가 있다**: P0-핵심을 먼저 끝까지 잇고, M2 통합 검증을 통과한 뒤 P0-나머지, 이어서 P1을 붙인다.
- **연락은 사장이 직접 한다**: 차곡은 연락할 고객과 문자 초안까지만 준비한다. 고객에게 문자·카카오톡·이메일을 보내는 기능은 만들지 않는다.
- **예약·보안은 원안 수준**: 정비소별 데이터 격리와 서비스 관리자 계정 분리까지만 한다. P1 계정 운영은 발급자가 직접 만드는 계정·첫 비밀번호 변경·사장의 약관 동의·비활성 정비사 토큰 차단까지다(D-60~D-62). 강제 로그아웃(토큰 무효화), 정지 정비소 토큰 즉시 차단, 동시 요청 잠금, 목적별 동의 이력, 정비 기록 무효 처리는 P2다. 같은 예약·같은 기록을 두 직원이 동시에 고칠 때 덮어쓰지 않는 처리(`version`), 정비 기록 수정 이력·예약 정정 이력, 같은 담당 정비사 + 같은 시작 시각 예약 제한은 MVP에 포함한다(D-42·D-51·D-53·D-55).
- **미리 만들지 않는다**: 아직 차례가 오지 않은 단계의 기능과 Non-goal 기능은 빈 화면, 연결되지 않은 버튼, 쓰지 않는 API나 테이블로 미리 만들지 않는다. P2는 M3 MVP 검증 전까지 문서로만 둔다. 단, 정비 구분값(외부·거절)처럼 팀이 "값은 처음부터"로 정한 것과 예약의 담당 정비사 칼럼(D-51)은 예외로 P0-핵심 스키마에 포함한다.
- **완료는 테스트까지**: 화면·API·시드·통합 실행에 핵심 로직 테스트까지 갖춰야 완료로 센다.
- **완성도 우선**: 기능 수보다 시나리오 A·B가 끝까지 막힘없이 시연되는 것을 우선한다.

> v7 범위 재배치(외부·거절 입력, 캘린더의 P0-나머지 이동)는 모두 확정됐다. 캘린더는 홈에 두고 월·주 보기다(일 보기·예약 화면 S-03은 폐지, D-54).

## 01 서비스 정의와 프로젝트 경계

> 차곡은 소규모 정비소를 위한 예약 CRM으로, 예약 일정과 고객·차량·정비 이력을 통합 관리하고, 축적된 정비 기록을 활용해 재점검 시기가 된 고객의 재예약을 지원하는 서비스이다.

고객은 가입하거나 직접 입력하지 않으며, 차곡도 고객에게 직접 발송하지 않는다. 1~5인 독립 카센터의 전화·현장 고객 관리를 대상으로 한다.

| 결정 | v14 기준 | 하지 않음 |
|---|---|---|
| 핵심 문제 | 정비 기록이 다음 연락과 재방문으로 이어지지 않는 문제 | 종합 ERP, 예약 중개 플랫폼 |
| 사용자 | 서비스 관리자(정비소를 열고 닫기만), 사장, 정비사. 차주는 간접 수혜자 | 고객 앱·가입·직접 예약 |
| 연락 | 연락 대상 목록과 문자 초안 준비. 발송은 사장이 자기 폰으로 | 서비스의 고객 직접 발송 |
| 대상 차량 | 일반 승용차·SUV | 대형 공식 센터, 사고 수리, 법인 차량 관리 |
| 프로젝트 | MVP = P0 + P1, P2는 M3 MVP 검증 후 선택. 레포 3개(`chagok-docs`·`chagok-backend`·`chagok-frontend`) | — |
| 성과 | 등록 → 방문 → 기록 → 주기 계산 → 재점검 대상 → 재예약 → 재방문이 시연에서 끊김 없이 이어짐 | 운영 성과나 시장 수요 입증 |

## 03 업무 흐름, 완료 조건, 진행 단계

대표 시연은 하나의 재방문 순환이다. 신규 접수, 재점검 연락, 방문 중 안내가 같은 데이터와 같은 주기 계산으로 이어진다.

| 흐름 | 정상 처리 | 완료 조건 |
|---|---|---|
| 예약 확인 | 홈의 목록·캘린더에서 예약 선택 → 같은 화면 패널에서 예약 목적·고객·차량·최근 이력(최근 방문 2회)·점검 주기 요약 확인 → 방문 완료(P0-나머지부터는 차량이 도착하면 방문 접수 = 진행중) | 페이지 이동 없이 확인. 전체 이력이 필요할 때만 차량 상세(총 방문 3회 이상일 때 "상세 이동" 활성) |

### 구현 순서

1. **P0-핵심**: cycle(주기 계산) → 고객·차량 등록 → 방문·정비 기록 → 재점검 대상·홈 요약·방문 중 안내(미리보기 포함) → 예약 등록·홈의 오늘 예약 목록·예약 상세 패널·방문 완료·예약 변경
2. **M2 통합 검증**: P0-핵심이 최소 화면으로 등록 → 기록 → 재점검 목록 → 예약 → 날짜별 예약 목록까지 끝까지 도는지 백엔드·프론트의 `develop`을 함께 띄워 시연한다. 못 미치면 P0-핵심을 먼저 보강하고 P0-나머지·P1 착수를 미룬다.
3. **P0-나머지**: 외부·거절·점검 결과 입력 → 홈 캘린더(월·주) → 방문 접수(진행중)·예약 취소·노쇼 → 담당 선택·중복 제한·재배정·지난 예약 정정 → 정비 기록 수정 → 고객·차량 기본 수정, 연락처 마스킹
4. **P1 (MVP 완성)**: 월평균 추정(1순위)부터 모두 넣는다.
5. **M3 MVP 검증**: P0·P1 전부 완료 정의(12장) 충족, T·X 테스트 통과, 빈 DB에서 시나리오 A·B·격리 시연. 통과해야 P2를 고른다.

## 04 계정·권한·정비소 운영

서비스 관리자는 정비소를 열고 닫을 수 있지만, 정비소 안을 들여다볼 수는 없다. P0에서는 관리 화면 없이 시드 계정으로 시작한다.

### 로그인 (JWT, 결정 3)

- 로그인에 성공하면 JWT 토큰을 받고, 이후 요청마다 토큰을 함께 보낸다. 서버는 로그인 상태를 따로 저장하지 않는다.
- 사장·정비사 토큰에는 계정 번호, 소속 정비소(`shop_id`), 역할(사장/정비사)이 들어 있다. 서비스 관리자 토큰에는 계정 번호와 서비스 관리자 역할만 있고 `shop_id`가 없다.
- 토큰이 없거나 만료되면 "로그인 필요"(401)로 답하고 화면은 로그인으로 보낸다. 역할이 맞지 않으면 "권한 없음"(403)이다.
- 로그인 실패는 "아이디 없음"과 "비밀번호 틀림"을 같은 문구로 답한다.
- 로그아웃은 화면에서 토큰을 지운다. 토큰을 서버에서 강제로 무효화하는 기능은 P2다.

원칙(D-57, D-24를 대체): **사장은 정비사가 할 수 있는 모든 일을 하고, 설정·계정·비활성화·삭제·파기를 더 한다.** 캘린더는 정비소 공용이라 사장·정비사 모두 전체 일정을 본다("내 담당만" 보기는 화면 필터일 뿐 데이터 권한이 아니다). 계정은 한 사람이 하나씩 쓰고 공유하지 않으며, 사장이 직접 정비하면 사장 계정이 담당 정비사가 될 수 있다. ○ 가능 · △ 조건부 · × 불가(403).

### 구조로 막는 방법

- 서비스 관리자 계정은 `staff`가 아닌 별도 테이블 `platform_admin`에 둔다. P0에서는 시드 서비스 관리자 1명만 두고, 이 계정으로 고객 목록에 접근하면 거부되는지 테스트한다(결정 7).
- 정비소 데이터 API는 토큰의 `shop_id`로만 조회한다. 서비스 관리자 토큰에는 `shop_id`가 없으므로 조회 기준 자체가 없다.
- 다른 정비소의 데이터를 요청하면 "없음"(404)으로 답한다. 거부(403)로 답하면 그 데이터가 있다는 사실이 드러나기 때문이다(결정 12).
- 서비스 관리자는 `/api/admin/**` API만, 사장·정비사는 정비소 API만 허용한다. 정비사가 사장 전용 기능이나 남이 담당한 기록·예약을 고치려 하면 403이고, 3일 제한을 넘기면 403 `EDIT_PERIOD_EXPIRED`다. 사장 전용·담당·기간 판정은 서버가 한 곳에서 하고, 화면에서 메뉴를 숨기는 것은 편의일 뿐이다.
- 반대 방향도 막는다. 사장·정비사 토큰으로 `/api/admin/**`를 부르면 403 `FORBIDDEN`이다(D-63 B10, 08 X18). 이것은 이미 구현되어 CI를 통과했다(chagok-backend#11, `EndpointGuardTest` E4).
- 정비소를 정지하면 로그인만 차단하고 데이터는 유지한다 (P1). 정지된 정비소의 이미 발급된 토큰까지 즉시 막는 것은 P2다. 비활성화된 정비사 계정은 로그인할 수 없고(P1, 403 `ACCOUNT_INACTIVE`), **비활성화 전에 받은 토큰으로도 정비소 API를 쓸 수 없다**(P1, D-62, 아래 「계정 상태 확인」).

이 경계는 서비스 기능(화면·API) 수준이다. 서버·DB 직접 접근, 토큰 무효화, 동시 로그인 정책은 MVP 범위 밖이다.

### 계정 발급·첫 로그인·약관 동의 (P1, D-60~D-62)

2026-11-23 팀 회의 확정(chagok-docs#65)이다. 구현은 P1이고 **아직 구현하지 않았다.** P1 이슈는 M2 통합 검증 통과 뒤에 연다(CONTRIBUTING 3장). 세부 계약은 08 0.6·03·24·26·32·35·51·52, 화면은 09 S-01·S-09·S-10, 테스트는 04 L1~L16·08 X19~X21에 있다(#67).

**계정 상태 확인 순서 (08 0.6)**: 보호된 정비소 요청마다 서버가 DB에서 ① 토큰의 계정 없음 → 401 ② 비활성(정비사, V3부터) → 403 `ACCOUNT_INACTIVE` ③ 비밀번호 변경 필요 → 403 `PASSWORD_CHANGE_REQUIRED`(03·24만 허용) ④ 사장이고 현재 약관 버전 동의 기록 없음 → 403 `TERMS_AGREEMENT_REQUIRED`(03·24·52만 허용) 순으로 본다. 토큰에 상태를 넣지 않으므로 재로그인 없이 같은 토큰으로 다음 단계에 간다. 서비스 관리자 API는 이 확인 대상이 아니다. 확인 위치·방식(`global/auth`가 부르고 `account`가 구현하는 인터페이스 등)은 **제안이며 아직 정하지 않았다**(11 3.3.1). P1 착수 전에 정하고, 정하면 CONVENTIONS 3장 표에 반영한다.

**비밀번호 변경 화면 (S-01, P1)**: 현재(임시)·새·새 확인 3칸. 입력 전 중립 도움말, 칸을 벗어날 때(blur) 조건 미충족이면 빨간 테두리 + 칸 아래 오류 문구(색만으로 전달하지 않음), 다시 맞추면 입력 중 즉시 해제. 표시/숨김 토글은 키보드·스크린리더로 쓸 수 있다. 빈 칸·조합 미충족·확인 불일치·요청 중이면 버튼 비활성. 성공하면 사장은 약관 단계(남았으면), 아니면 홈. 오류 문구 예: "영문·숫자·특수문자를 모두 포함하여 8~20자로 입력해 주세요." / "새 비밀번호가 일치하지 않습니다."

**만들지 않는 것 (00 기준)**: 정비소·고객 셀프 회원가입(정비소 셀프 온보딩은 P2 C 묶음), 고객 앱·고객 로그인, 소셜 로그인, 이메일·SMS 인증과 자동 발송, 결제, 약관 버전 관리 화면·정기 재동의, 필요 이상의 감사·보안 체계, 역할 변경·직원 소속 이동·계정 삭제.

## 05 고객·차량 등록

고객명·연락처·차량번호·차종 네 가지만으로 시작한다(D-58). 고객과 차량은 독립 ID로 연결하고, 전화번호나 차량번호를 PK로 쓰지 않는다.

| 정책 | v14 기준 |
|---|---|
| 등록 시점 | 현장 첫 방문 때, 또는 전화 예약 때 확인한 정보로 미리 등록 (P0-핵심) |
| 조회 우선 | 차량번호나 연락처로 먼저 조회해 기존 고객인지 확인한 뒤 신규만 등록 |
| 차량번호 중복 | 시스템이 차단하지 않음 |
| 기존 고객의 새 차량 | 고객을 새로 만들지 않고 차량만 추가 (고객 1:N 차량) |
| 차량 정보 | 차종은 필수. 연식(1980 ~ 현재 연도+1, B04)·주행거리(정수 0~2,000,000km, B03, 벗어나면 400 `INVALID_INPUT`)는 확인 가능할 때 추가하고 비어 있어도 등록할 수 있지만, 차량에 비어 있으면 정비 시작(방문 접수) 때 필수, 접수를 거치지 않으면 정비 기록 첫 저장 때 서버가 요구한다 (D-58) |
| 기본 수정 | 고객·차량 정보 수정, 안내 수신 동의 변경 (P0-나머지) |
| 연락 정보 | 안내 수신 동의 하나만(D-25). 번호 오류·연락 거부는 P1 연락 결과로 |
| 안내 수신 동의 | 기본값 체크 안 됨. 고객에게 물어보고 동의하면 체크한다 (결정 11). 동의하지 않은 고객은 재점검 대상 목록과 문자 초안에 나오지 않는다 |
| 개인정보 | 목록 화면(홈의 예약 목록·캘린더, 재점검 대상, 고객 목록)에서 연락처 마스킹(P0-나머지). 마스킹은 서버가 한 곳에서 하고 규칙은 B07(04A, 08 0.5)로 확정됐다(대표 예 `010-****-0001`, 길이·국번이 달라도 원번호가 드러나지 않음). 상세 화면(고객 상세·차량 상세·예약 상세 패널)과 문자 초안 화면은 전화를 걸고 발송해야 하므로 전체 번호를 보여준다 (D-40). 주민번호·주소 등은 받지 않음. 시연은 가상 데이터 |
| 비활성화·삭제 (P1, D-56) | 사장만. 이력(정비 기록·예약)이 없는 고객은 삭제(이력 없는 차량 포함), 이력이 있으면 비활성화. 차량은 영구 보존이라 비활성화만. 비활성 고객·차량은 검색에서 기본 제외, 재점검 대상·홈 숫자에서 제외, 새 예약·정비 기록 불가(기존 기록은 조회 가능), 사장이 재활성화할 수 있다 |
| 보관·익명화 (P1, D-56) | 마지막 방문일(없으면 등록일) + 5년이 지나면 사장이 확인하고 이름·연락처를 익명화한다. 자동이 아니다(서버 스케줄러 없음). 차량·정비 이력·예약은 보존. 법적 근거는 PM이 확인하고(05 POL-46) 구현 이슈는 그 확인 뒤에 연다 |

방문 이력이 없는 고객·차량은 주기 상태가 "미확인"으로 표시된다. 동의 철회 이력(P2)과 소유주 변경은 다루지 않는다. 시드 데이터는 시연을 위해 대부분 동의 상태로 넣는다.

## 06 예약·방문

예약은 차곡의 기본 기능이다. 전화로 받은 예약을 정비소가 직접 입력하고, P0-핵심은 홈의 날짜별 예약 목록과 예약 상세 패널, P0-나머지는 홈 캘린더(월·주)로 본다. 기능은 가볍게 두되, 예약에서 고객·차량·이력으로 바로 이어지는 연결은 P0-핵심이다. 예약에는 담당 정비사가 있고, 사장·정비사 모두 담당이 될 수 있다.

| 대상 | v14 기준 |
|---|---|
| 예약 등록 | 일시·차량·예약 목적·담당 정비사 입력 (P0-핵심). 예약 목적은 정비 항목 선택(여러 개) + 기타 + 메모, 선택 입력. 목적이 모호한 전화 예약도 받을 수 있게 비워 둘 수 있다. 담당 정비사(D-51): P0-핵심은 서버가 예약을 등록한 계정을 담당으로 자동 지정(입력 칸 없음), P0-나머지부터 등록 때 고른다(기본: 로그인 계정) |
| 예약 조회 | P0-핵심: 홈의 날짜별 예약 목록(오늘, 앞뒤 날짜 이동, 취소 예약도 상태 라벨로 표시하고 "오늘 예약 N건"은 취소 제외, B05) + 예약 상세 패널. P0-나머지: 홈 캘린더 월·주(라이브러리 없이 직접 구현, 결정 16). 예약 메뉴·화면은 따로 없다 (D-54) |
| 예약 시각 | 30분 단위 시작 시각만, 예상 소요 시간 없음 (D-21) |
| 중복 | 같은 차량은 유효 예약(상태 예약 + 예약 날짜 ≥ 오늘, 또는 진행중) 1건만. 같은 시각 다른 차량은 허용 (D-22). P0-나머지부터 같은 담당 + 같은 시작 시각의 유효 예약은 막고(409 `MECHANIC_SLOT_CONFLICT`), 같은 시각 다른 담당은 허용한다. 소요 시간이 없어 "같은 시간대" = 같은 시작 시각이다 (D-51) |
| 지난 예약 | 등록·변경은 오늘 이후 날짜만(오늘은 지난 시각 허용). 시각이 지난 "예약"은 "처리 필요" 표시, 방문 완료·취소·노쇼로 정리 (D-23). 처리 안 된 어제 이전 "예약"은 유효 예약이 아니라서 그 차량에 새 예약을 잡을 수 있다 |
| 예약 상태 | 예약 → 진행중(방문 접수) → 방문 완료 / 취소 / 노쇼. 예약 → 방문 완료 직접 전이도 허용. 방문 완료·변경은 P0-핵심(D-42), 진행중·취소·노쇼는 P0-나머지(D-52). 노쇼는 상태 "예약"이고 시각이 지난 예약에만, 노쇼 관리는 P2 (D-27). 진행중은 변경·재배정·노쇼 불가, 완료·취소만 가능 |
| 방문 접수 | 상태 "예약"을 "진행중"으로 바꾼다(차량 도착, 시각 전·후 모두, P0-나머지, D-52). 차량의 연식·최근 주행거리가 비어 있으면 이때 입력한다(D-58). 진행중 예약은 담당의 시작 시각을 계속 점유한다 |
| 지난 예약 정정 | 예약 날짜가 지난 예약과 끝난 예약(완료·취소·노쇼)은 일시·고객·차량·담당을 바꿀 수 없고 상태·메모만 정정한다(P0-나머지, D-53). 취소↔노쇼, 취소·노쇼→완료는 사장만, 완료→취소·노쇼는 불가, 메모는 사장 또는 담당 정비사(예약 날짜 + 3일 이내). 모든 정정은 이력(`reservation_revision`)에 남는다 |
| 담당 재배정 | 상태 "예약"만, 예약 날짜 전날까지(사장·정비사). 사장만 당일에도 가능하며 사유가 필수이다(진행중·지난 날짜는 불가). 재배정도 이력에 남는다 (P0-나머지, D-53) |
| 방문 완료 | 방문 완료로 처리된 예약은 정비 이력 등록 화면으로 이어짐 |
| 현장 방문 | 예약 없이 바로 정비 이력을 등록할 수 있음 |
| 재점검 연결 | 재점검 대상 목록에서 바로 예약 등록. 예약한 차량은 목록에 남고 "예약 있음"으로 표시 (결정 13) |

### 예약 상세 패널 (P0-핵심, 2026-11-22 회의 결정 5)

예약을 고르면 페이지를 옮기지 않고 같은 화면의 패널에 아래를 보여준다. 자주 하는 작업은 짧게, 상세 정보는 필요할 때 펼친다.

| 항목 | 내용 |
|---|---|
| 예약 | 일시, 상태, 담당 정비사(P0-나머지부터 이름·색), 예약 목적(고른 항목·기타·메모) |
| 고객·차량 | 고객명, 연락처(전체 번호. 상세 화면이므로 마스킹하지 않음, D-40), 차량번호, 차종·연식, 최근 주행거리 |
| 최근 정비 이력 | 최근 방문 2회. 총 방문이 3회 이상이면 "상세 이동" 버튼(→ 차량 상세)이 활성이고 미만이면 비활성. 버튼은 항상 보인다 (D-54) |
| 점검 주기 요약 | 6개 항목의 미확인/여유/임박/도래 (cycle 결과 그대로, 정상·불량 표현 없음). 항목은 `sortOrder` 순이고, 예약 목적으로 고른 항목은 순서를 바꾸지 않고 강조만 한다(B02). "지난 방문 거절"·"지난 점검 주의(메모)"는 P0-나머지부터 표시 |
| 다음 작업 | 방문 완료(→ 정비 기록), 변경, 차량 상세로 이동(전체 이력). P0-나머지: 방문 접수, 취소·노쇼, 지난 예약 정정, 정정·재배정 이력 보기 |

- 패널은 홈의 날짜별 목록(P0-핵심)과 홈 캘린더(P0-나머지, 월의 날짜 목록 패널·주 카드)가 함께 쓴다.
- 화면 폭 1024px 이상은 오른쪽 패널, 미만은 화면 전체를 덮는 패널(닫기·뒤로 가기로 복귀) (D-26의 배치 규칙. 최근 방문 표시는 D-54로 바뀜).

### 차량 약식 도면 (P1, 읽기 전용)

읽기 전용 보조 화면으로만 둔다. 도면에서 부위를 고르거나 점검 결과를 입력·수정·저장하지 않는다. P1에서 차량 상세에 둔다. 도면의 6개 항목 위치(엔진오일, 에어클리너, 에어컨필터, 브레이크패드, 타이어, 배터리)에 점검 주기 상태 색(미확인/여유/임박/도래)을 표시하며, 색은 `StatusBadge`와 같은 기준을 쓴다. 상태는 cycle 결과를 그대로 쓰고 새로 계산하지 않는다. 도면은 특정 제조사 차량 그림이 아닌 일반 약식 도면을 쓴다.

### 캘린더를 P0-나머지에 두는 이유

캘린더 직접 구현은 구현 부담이 가장 큰 결정이었다. 예약 CRM에서 캘린더는 중요한 UI지만, 순환을 끝까지 잇는 데는 날짜별 목록과 상세 패널로 충분하므로 P0-핵심은 같은 API를 쓰는 날짜별 목록으로 순환을 완성하고 캘린더는 M2 통합 검증 이후에 붙인다. 주 보기는 같은 예약 조회 API(기간 조회)를 다른 모양으로 보여주는 화면이라 목록을 먼저 만들어도 API를 다시 고치지 않고, 월 보기만 날짜별 건수 요약 API가 하나 더 필요하다.

### 홈 캘린더 직접 구현 범위 (P0-나머지, D-54)

캘린더는 정비소당 공용 하나이고 홈에 둔다. 월 보기와 주 보기 두 가지만 만든다(일 보기는 폐지). **월 보기**는 날짜별 총 건수(취소만 제외, 진행중·노쇼는 포함)와 상태별 건수(예약·진행중·완료·취소·노쇼)를 보여주고, 날짜를 누르면 그날 목록 패널이 열리며 거기서 예약을 고른다. **주 보기**는 7일 × 30분 칸에 시각·차량번호·고객명 상세 카드를 둔다. 표시 시간대는 기본 08:00~20:00(시작 칸 08:00~19:30)이고, 08:00 전에 시작하는 예약은 위, 20:00 이후 시작은 아래 별도 영역에 보여 빠뜨리지 않는다(B08). 담당 정비사는 색과 이름 라벨을 함께 보여주고(색만으로 구분하지 않음), "내 담당만" 토글은 보기 필터일 뿐 권한이 아니다. 드래그로 일정 옮기기와 반복 예약은 만들지 않는다(P2). 일시 변경은 수정 화면으로 한다. 주 보기는 기간 조회 API, 월 보기는 날짜별 요약 API를 쓰고, 예약을 고르면 같은 상세 패널을 연다.

영업시간, 수용량, 정비사별 근무 시간표, 노쇼 관리(횟수·경고·자동 처리), 동시 요청 잠금은 P2다. 같은 담당 + 같은 시작 시각의 중복 제한은 MVP로 옮겼다(D-51).

## 07 정비 기록과 항목

방문 한 번에 여러 항목을 기록하고, 항목마다 교체인지 점검인지 구분한다. 이 구분이 주기 계산의 근거가 된다.

| 구분 | 의미 | 주기 | 범위 |
|---|---|---|---|
| 교체 | 우리 정비소에서 실제 교체·수행 | 다시 시작 | P0-핵심 |
| 점검 | 상태만 확인. 점검 결과(양호/주의)와 메모를 함께 남길 수 있음 | 유지 (결과와 상관없이) | P0-핵심, 점검 결과 입력은 P0-나머지 |
| 외부 | 고객이 다른 곳에서 했다고 진술 | 다시 시작 (고객 진술 표시) | 값은 P0-핵심, 입력은 P0-나머지 |
| 거절 | 권유했으나 고객이 거절 | 유지, 다음 목록·미리보기에 "지난 방문 거절" 표시 | 값은 P0-핵심, 입력은 P0-나머지 |

구분값 4개를 처음부터 정의해 두었기 때문에(결정 6), 외부·거절 입력을 여는 데 필요한 것은 기록 화면의 구분 선택지와 출처 표시뿐이다. cycle의 기준 기록 규칙(08장)은 처음부터 외부를 반영하고, 거절은 주기를 바꾸지 않으므로 별도의 재안내 로직이 필요 없다.

**점검 결과 (P0-나머지)**

| 규칙 | 내용 |
|---|---|
| 값 | 양호 / 주의. 구분이 "점검"일 때만, 선택 입력. 메모를 함께 남길 수 있음 |
| 의미 | 정비사의 관찰 기록. 진단이나 정비 결과 보증이 아님 |
| 주기 | 바꾸지 않음. 주기 상태(미확인/여유/임박/도래)와 대상 목록 기준은 그대로 |
| "주의" 표시 | 그 항목의 가장 최근 기록이 "점검·주의"인 동안 표시. 같은 항목이 다시 기록되면(교체·점검·외부·거절) 사라짐 |
| 표시 위치 | 예약 상세 패널, 방문 접수 미리보기, 재점검 대상 목록(이미 목록에 있는 차량에 표시만. 주의만으로 목록에 올리지 않음) |
| 판정 위치 | cycle ("지난 방문 거절"과 같은 방식으로 가장 최근 기록에서 판정) |

### 정비 항목과 주기 (결정 1, 확정)

| 항목 | 개월 | km |
|---|---|---|
| 엔진오일 | 6 | 10,000 |
| 에어클리너 | 12 | 15,000 |
| 에어컨필터 | 6 | 10,000 |
| 브레이크패드 | 12 | 20,000 |
| 타이어 상태 점검 | 6 | 10,000 |
| 배터리 | 36 | 60,000 |

- 항목·주기는 시드 데이터로 넣는다. 주기값을 코드에 고정하지 않고 데이터로 두어, P1 기준표 수정 기능이 데이터만 바꾸면 되게 한다.
- 기록 항목: 방문일, 주행거리, 정비 항목, 구분, 담당 정비사, 메모. 담당 정비사는 P0-핵심에서 기록을 저장한 계정이고, P0-나머지부터 저장할 때 고른 사람이다(기본: 예약의 담당 또는 로그인 계정, 정비사도 다른 정비사로 지정할 수 있음, D-51).
- 한 방문의 여러 항목은 항목마다 1행으로 저장하고, 같은 방문은 묶음 번호(`visit_key`)로 연결한다(결정 4). 화면과 API에는 "방문 한 건에 항목 여러 개" 모양으로 보여준다.
- 외부 정비는 확인 가능한 날짜·주행거리만 기록하고, 출처를 "고객 진술"로 남긴다.
- 주행거리는 정수 0~2,000,000km이고(B03, DB CHECK는 ≥ 0이고 상한은 서버 검증) 기록에서는 비워둘 수 있다. 단 차량의 연식·최근 주행거리가 비어 있으면 교체·점검을 저장할 때 입력해야 한다(방문 접수를 거쳤다면 이미 입력되어 있음, D-58).
- 정비소별 항목·기준표 설정 화면은 P1이다. 수정은 사장만(D-57)이고, 6개 항목의 켜기·끄기·개월·km만 바꾼다. 새 항목 추가는 P2다(D-59).

### 정비 기록 수정 (P0-나머지, D-55)

| 규칙 | 내용 |
|---|---|
| 수정 범위 | 방문일(미래 불가)·주행거리·구분·항목·점검 결과·메모·담당 정비사. 차량은 바꿀 수 없다. 삭제는 없다 |
| 권한 | 사장은 모든 기록·기간 제한 없음. 정비사는 본인이 담당한 기록만, 방문일 기준 3일 이내(외부 기록은 저장일 기준) |
| 이력 | 수정할 때마다 수정자·수정 날짜·수정 전 값을 남기고(`maintenance_record_revision`), 차량 상세에서 "수정됨" 꼬리표로 바뀐 부분을 보여준다. 사유는 선택 |
| 주기 | 상태를 저장하지 않으므로 수정한 날짜·구분이 바로 다음 정비일·상태·재점검 대상에 반영된다. 차량의 최근 주행거리는 수정값이 더 클 때만 갱신 |
| 동시 수정 | `version`으로 충돌을 처리한다(409 `CONCURRENT_MODIFICATION`) |
| 무효 처리 | 잘못 넣은 기록(다른 차량 등)의 무효 처리는 후속 P2다. 그 전에는 구분을 점검·거절로 바꾸고 메모로 남긴다 |

## 08 주기 계산 정책

항목마다 개월과 km 기준을 둔다. P0에서 날짜 판정은 개월 기준만 쓰고, km 기준은 주행거리를 입력하는 방문 접수 때 비교한다. 계산은 서버의 한 곳(cycle)에서 하고, 차량 상세·방문 접수 미리보기·재점검 대상 목록·홈 요약·문자 초안이 같은 결과를 쓴다. 상태는 저장하지 않고 볼 때마다 계산한다.

상태는 **점검 시기 안내**이지 실제 부품 상태 진단이 아니다. 화면에 정상·불량처럼 단정하는 표현을 쓰지 않고, 확인하지 않은 항목은 "미확인"으로 둔다. 실제로 교체·점검한 항목만 수행 이력에 남고, 권유만 한 항목이나 점검하지 않은 항목을 양호로 추정하지 않는다. 점검 때 관찰한 결과는 양호/주의로 남기며(07장), 이것도 주기 상태를 바꾸지 않는다.

| 판정 규칙 | 기준 | 범위 |
|---|---|---|
| 기준 기록 | 해당 항목의 마지막 교체 또는 외부 정비 중 더 최근 것. 점검·거절은 기준이 되지 않음 | P0-핵심 (외부 입력은 P0-나머지) |
| 기간 기준 | 기준 기록일 + 설정 개월 = 다음 정비 시점. 재점검 대상 목록과 상태 표시의 날짜 기준 | P0-핵심 |
| 거리 기준 (방문 때) | 방문 접수 때 입력한 주행거리 ≥ 기준 기록 km + 주기 km이면 "도래". 기준 기록에 주행거리가 없으면 거리 판정 생략 | P0-핵심 |
| 저장 전 미리보기 | 방문 접수 화면에서 주행거리를 입력하면, 기록을 저장하기 전에 위 규칙으로 계산한 항목 상태를 바로 보여줌. 미리보기는 기록을 남기지 않음 (결정 10) | P0-핵심 |
| 거절 표시 | 항목의 가장 최근 기록이 기준 기록 이후의 거절이면 "지난 방문 거절(날짜)"을 함께 반환. 상태 판정에는 영향 없음 | P0-나머지 |
| 거리 → 날짜 환산 | 주행거리 기록 2회 이상일 때 월평균 주행거리를 추정해 km 기준을 날짜로 환산, 기간 기준과 먼저 오는 쪽을 사용 | P1 (1순위) |
| 미확인 | 기준 기록이 없음 | P0-핵심 |
| 도래 | 오늘 ≥ 다음 정비 시점, 또는 방문 때 km 기준 이상. 기준과 같아도 도래 (결정 9) | P0-핵심 |
| 임박 | 오늘 + 달력상 1개월 ≥ 다음 정비 시점 (결정 8) | P0-핵심 |
| 여유 | 다음 정비 시점까지 달력상 1개월 넘게 남음 | P0-핵심 |

- 달력상 1개월은 일수(30일)가 아니라 날짜로 센다. 예: 다음 정비일이 4월 15일이면 3월 15일부터 임박이다. 1월 31일 + 1개월은 2월 말일로 계산한다.
- P0에서는 km만 넘은 차량이 방문 전 재점검 대상 목록에 뜨지 않는다. 이는 P1 거리 → 날짜 환산으로 보완한다.
- 표시되는 항목은 차량 상태 진단이 아니라 "확인이 필요한 항목"으로 안내한다.
- 월말·윤년 같은 날짜 경계, 기준과 정확히 같은 날·같은 km(도래), 주행거리 없는 기록, 미확인, 교체 vs 점검·거절, 외부 정비 후 재시작, 거절 표시는 테스트로 확인한다.
- 정비 기록을 수정하면(P0-나머지, D-55) 수정한 날짜·구분이 바로 다음 정비일·상태·재점검 대상에 반영된다(상태를 저장하지 않으므로 이관이 없다).

## 09 재점검 대상과 연락

재점검 대상 목록이 이 서비스의 중심 화면이다. 연락은 서비스의 발송이 아니라 사장의 전화·문자 업무이며, 차곡은 그 준비(대상, 문구, 기록)까지만 맡는다.

### 대상 목록 (P0)

| 기능 | 범위 | 기준 |
|---|---|---|
| 대상 선정 | P0-핵심 | 도래·임박 항목이 있는 차량(개월 기준). 안내 수신에 동의한 고객만 (동의 기본값은 체크 안 됨). 비활성 고객·차량은 제외 (P1) |
| 목록 표시 | P0-핵심 | 고객·차량별로 묶고, 항목·상태·근거(마지막 기록일·거리) 표시. 도래 먼저 |
| 예약 있는 차량 | P0-핵심 | 목록에서 빼지 않고 "예약 있음"으로 표시 (결정 13). 같은 고객에게 두 번 연락하는 것을 막고, 예약이 취소되면 바로 다시 연락 대상이 됨 |
| 예약 연결 | P0-핵심 | 목록에서 바로 예약 등록 |

- **방문 묶음 번호(visit_key)**: 방문을 따로 표로 두지 않고, 한 방문에서 저장한 항목들에 같은 번호를 붙인다(결정 4). 방문 정보(방문일·주행거리·담당 정비사)는 한 번에 저장하고, 저장 뒤 수정(P0-나머지)은 기록 1행 단위다(D-55). 방문 메모·사진·예약 연결처럼 방문 단위 정보가 늘거나 잘못 넣은 기록의 무효 처리가 필요해지면 방문 테이블로 나눈다(P2).
- **DB 구조 관리 (Flyway, 결정 17)**: 테이블 구조는 변경마다 버전 파일(V1, V2…)로 남기고, 이미 공유된 버전 파일은 고치지 않고 새 파일을 더한다. 팀원 누구의 DB든 같은 순서로 같은 구조가 된다. V1 = 9개 테이블(복합 FK 8개, `staff` `UNIQUE(shop_id, id)`, 담당 정비사 칼럼 2개 포함). V2 = P0-나머지(점검 결과, 예약 상태 `IN_PROGRESS`·`NO_SHOW`, `customer`·`vehicle`의 `version`, 정비 기록의 `updated_at`·`version`, 이력 표 2개. 복합 FK는 10개), 한 파일로 DB 담당자가 먼저 만든다. V3 = P1(`customer.status`·`anonymized_at`, `vehicle.active`, `staff.active`, `contact_log`). 약관 동의 기록 표를 V3에 넣을지 별도 버전으로 둘지는 DB 담당자가 정한다. **2026-11-24 현재 backend에 적용된 버전 파일은 V1뿐이고, V1과 시연 시드는 고치지 않는다.**
- **시연 시드**: `chagok-backend/db/seed/demo_seed.sql`을 시연 전용 DB에만 실행기로 넣는다(서버 자동 삽입 금지, D-43). 오늘 기준 상대 날짜로 넣어 미확인·여유·임박·도래가 고루 나오게 한다(M5 최종 시연 전날 시연 DB를 새로 만든다). 시연 계정 비밀번호는 1234(BCrypt, D-44). A 정비소의 담당 정비사 후보는 사장·정비사 2명이고(B 정비소는 사장 1명), 시드 예약·정비 기록의 담당이 채워진다. 기대값은 홈 "오늘 예약" 2건, "오늘 연락할 고객" 5명, 재점검 대상 6대(07 7.5)이다.
- **P1에서 추가할 것(V3)**: 연락 결과 기록을 시작할 때 연락 기록 표 `contact_log`(정비소, 고객, 결과 6개 값, 메모, 연락일, 기록한 계정, `shop_id` 직접·고객과 복합 FK)를 더한다. 알림 시간은 브라우저에 저장하므로(D-59) `staff`에 열을 더하지 않는다. 같은 V3에서 `customer.status`·`anonymized_at`, `vehicle.active`, `staff.active`가 더해진다(D-56·D-57). 쓰지 않는 테이블·열을 미리 만들지 않는다.
- **삭제·익명화 (P1, D-56)**: 삭제는 이력(정비 기록·예약)이 없는 고객과 그 고객의 이력 없는 차량에 한해 서버가 자식부터 지운다. 정비 기록은 삭제하지 않는다(수정은 D-55). 5년 경과 고객의 익명화는 행을 지우지 않고 값을 바꾼다(이름 "(삭제된 고객)", 연락처 빈 문자열, 동의 해제). 고객 행이 남으므로 차량의 복합 FK가 그대로 유지되어 차량·정비 이력이 보존된다. 법적 근거 확인(05 POL-46) 전에는 구현 이슈를 열지 않는다.

| 3 | 최초 동의 후 재로그인 | 03이 "역할 사장 + 그 정비소에 현재 버전 행이 있는가"로 `termsAgreementRequired`를 계산하므로 다시 묻지 않는다. 사장 비밀번호 재발급(35) 뒤에도 약관은 다시 묻지 않는다 | 기존 설계와 일치 |

| 5 | 계정·정비소 상태와 접근 제한 | 확인 순서 비활성 → 비밀번호 변경 → 약관(08 0.6). 정비사·서비스 관리자는 약관 확인 대상이 아니다. 정비소 정지는 로그인만 막고 기록은 그대로다. 계정·정비소 삭제 기능이 없으므로(C09) FK 삭제 동작이 실제로 쓰이는 경로는 없다 | 기존 설계와 일치 |
| 6 | API 52 저장 계약 | 요청 `termsVersion`이 서버의 현재 버전과 같을 때만 저장(다르면 400), `accepted_at`은 서버 시각, 응답 `shopId`·`termsVersion`·`acceptedAt`. 비밀번호 변경 전이면 403 `PASSWORD_CHANGE_REQUIRED` | 기존 설계와 일치 |
| 7 | API 03 온보딩 상태 조회 | `passwordChangeRequired`·`termsAgreementRequired`·`termsVersion`. 현재 약관 버전을 두는 곳(서버 설정)과 값 형식은 약관 전문 확정 때 정한다 | 기존 설계와 일치, 버전 형식 대기 |
| 8 | 새 Flyway 버전 필요 여부 | **필요하다.** 이미 적용된 V1은 고칠 수 없고 V2(P0-나머지)에는 넣지 않는다. V3(P1)에 넣을지 별도 버전으로 둘지는 DB 담당자 결정 | DB 담당자 결정 |
| 9 | DB 담당자 검토가 필요한 제약·인덱스·칼럼 | 표·칼럼 이름(`staff_id` vs `accepting_staff_id`), `terms_version` 길이, 단일 FK vs 복합 FK, `UNIQUE(shop_id, terms_version)`가 `shop_id` FK 인덱스를 겸하는지와 `staff_id` FK 인덱스, `created_at`과 `accepted_at`을 둘 다 둘지, 07 6.1 이름 규칙(제약·인덱스 이름 길이 포함), 시연 시드에 A·B 정비소 동의 행을 넣을지(넣지 않으면 P1 이후 시연 사장이 첫 로그인에서 약관 단계를 거침 — 시드 변경은 `chagok-seed-data`로 따로) | **DB 담당자 검토 필요** |
| 10 | 검증 테스트 | 문서: 04 L9~L11, 08 X16(서비스 관리자 토큰으로 52 → 403)·X21. DB(그 버전 PR에서 07 6.3 형식): 빈 DB 적용 → 재실행 up to date, UNIQUE·FK·NOT NULL 위반 INSERT 실패, V1·V2 정합성, JPA `ddl-auto: validate`. 구현: 52 동시 중복 요청 시 기록 1건 | 검증 대기 |

## 11 코드 책임·화면·기술

주기 계산은 한 모듈에만 두고, 다른 화면은 그 결과를 가져다 쓴다. 이것만 지키면 구조는 단순하게 간다.

| 모듈 | 책임 |
|---|---|
| account / shop | 로그인(JWT)·역할·정비소 소속 확인(토큰의 `shop_id`는 `global/auth`의 로그인 정보). `account.api`로 담당 정비사가 그 정비소의 활성 사장·정비사인지 확인해 준다(D-51·D-55). 정비사 계정 추가·비활성화·임시 비밀번호 재발급, 비밀번호 변경, 약관 동의 기록, 요청마다 하는 계정 상태 확인(비활성·비밀번호 변경·약관. 위치·방식은 제안, 11 3.3.1) (P1, D-60~D-62) |
| customer/vehicle | 고객·차량 조회·등록·수정, P1 비활성화·삭제·익명화 |
| item | 정비 항목과 개월·km 주기(`service_item`). 예약 목적과 정비 기록이 `item.api`로 확인 |
| reservation | 예약 등록·변경·취소, 방문 접수(진행중), 담당 재배정, 지난 예약 정정, 기간별 예약 조회 (홈의 날짜별 목록과 월·주 캘린더가 같은 API를 쓰고, 월 보기는 날짜별 건수 요약 API를 더 쓴다) |
| 예약 상세 패널 (화면 조립) | 예약 + 고객·차량 + 최근 정비 이력 + 점검 주기 요약을 한 응답으로 조립 (cycle 결과 사용). 저장하지 않음 |
| maintenance | 정비 이력 기록 (방문 단위 저장, visit_key, 구분값 4개, 점검 결과), 정비 기록 수정·수정 이력 (P0-나머지) |
| cycle | 마지막 기록과 주기 설정으로 항목 상태 계산(개월 판정, 방문 때 km 비교, 거절 표시). P1 월평균 추정도 이 안에만 추가. 다른 모듈에 의존하지 않음 |
| target (`screen/target`) | 재점검 대상 목록(예약 있음 표시 포함), 홈 요약 (cycle 결과 사용) |
| visit (`screen/visit`) | 방문 중 안내, 저장 전 미리보기, 차량 상세의 항목 상태 (cycle 결과 사용) |
| contact (P1) | 문자 초안 생성(target 결과 사용), 연락 결과 기록. P1 착수 때 만든다 |
| stats (P1, `screen/stats`) | 신규·재방문 고객 집계 |

세부 패키지 구조와 모듈 사이 호출 규칙은 `CONVENTIONS.md` 2·3장에서 정한다(D-20, M1 설계 확정에서 현행안 그대로 승인, chagok-docs#46). 요점은 다음과 같다.

- 다른 도메인은 그 도메인의 `api`(interface·record·enum)로만 부른다. 의존 방향은 외래키 방향과 같다.
- `reservation → account.api`, `maintenance → account.api`: 담당 정비사가 그 정비소의 활성 사장·정비사인지 확인한다(담당은 요청 값이므로, D-51·D-55). 담당 검증은 P0-나머지부터 필요하고(P0-핵심은 토큰의 계정이 담당), account 쪽은 reservation·maintenance를 부르지 않는다. `reservation`·`maintenance`는 `customer.api`·`item.api`도 부를 수 있다.
- "방문 완료 → 정비 기록 등록"은 코드 호출이 아니라 프론트의 화면 이동이다. reservation이 maintenance를 부르지 않는다.
- `cycle`은 다른 도메인·Spring·JPA를 모른다. `screen`은 표가 없고 아무도 import하지 않는다.

## 12 검증 계획과 완료 기준

완료 기준은 시나리오 A·B가 다른 팀원 환경에서도 끝까지 막힘없이 시연되는 것이다. 검증은 재방문 축과 격리에 집중한다.

### 기능별 완료 정의

기능 하나는 아래가 모두 갖춰져야 완료로 센다(00 7장). 하나라도 빠지면 미완료이며, M4 기능 동결 이후 시연에 넣지 않는다.

1. 요구사항·정책: 03 요구사항, 04 기능 규칙, 05 정책을 지킨다.
2. API 계약: 요청·응답·에러 코드가 08(표·JSON 예시)과 같고, 공통 응답·공통 오류 처리 규칙을 따른다.
3. 정상·오류·경계: 정상 흐름과 입력 오류·경계값·상태 전이 오류가 의도대로 동작한다.
4. 권한·격리: 역할별 권한(06)과 정비소 격리(08 X-xx)를 지킨다.
5. 테스트: 관련 테스트(04의 T·R·H·K, 08의 X, ArchitectureTest)를 함께 쓰고 CI에서 통과했다. 실행하지 못한 테스트는 이유와 함께 "미검증"으로 남긴다.
6. 회귀: 기존 기능에 영향이 없음을 확인했다(CI 전체 통과 + 관련 화면 확인).
7. 연결 실행: 화면이 실제 API와 연결되고, 백엔드·프론트가 각 레포의 `develop`에 모두 들어가 함께 띄워 다른 팀원이 빈 DB에서 확인했다. 시연에 쓸 시드 데이터가 있다.
8. 문서: 바뀐 명세가 `chagok-docs`에 반영되었다.
9. 담당자 확인: 담당 개발자가 위 항목을 직접 확인했다. AI가 "완료"라고 보고해도 실제 빌드·테스트 결과가 없으면 완료가 아니다(D-48).

## 13 확장 계획(P2)과 Non-goal

P2는 **M3 MVP 검증을 통과하기 전까지 문서로만 두고 코드·테이블·화면을 만들지 않는다.** 통과하면 A 묶음부터 `결정` 이슈로 하나씩 골라 추가하고, 하나를 완료 정의까지 마친 뒤 다음을 고른다. 항목마다 지금 구조에 이미 준비된 것과 그때 추가할 것을 적어, 확장 경로를 보여주는 것이 목적이다. 재방문 축과의 거리에 따라 세 묶음으로 나눈다.

### A. 재방문 축 강화 (우선순위 1)

P1의 "대상 목록 + 문자 초안 + 연락 기록"을 넓히는 확장이다. 고객 발송은 여전히 하지 않는다. 지금 수동으로 하는 "목록 보고 연락하기"를 넓히고, 그 효과를 숫자로 보는 순서다.

| 항목 | 내용 | 지금 준비된 것 | 그때 추가할 것 |
|---|---|---|---|
| 연락 대상 유형 확장 | 정비 시기 외에 거절 후속, 장기 미방문, 방문 후 안부 대상을 목록 탭으로 분리 | 거절 구분값과 표시(P0), 연락 결과 기록·문자 초안(P1) | 유형별 선정 규칙(예: 마지막 방문 후 N개월), 유형별 초안 |
| 문자 템플릿 관리 | 정비소별 문구 수정, 유형별 템플릿 | 고정 템플릿과 변수 치환(P1) | 정비소별 템플릿 테이블, 변수 목록, 수정 화면 미리보기 |
| 사장 알림 고도화 | 탭을 닫아도 사장이 고른 시간에 알림 | 탭 열린 상태 브라우저 알림, 알림 시간 설정(P1, 브라우저에 저장) | 서비스 워커, 푸시 구독 저장, 서버 스케줄러, PWA(iOS는 홈 화면 추가 필요) |
| 운영 리포트 | 재방문율, 연락 → 예약 전환율, 항목별 권유 수락률 | 구분값(P0), 연락 결과·신규·재방문 집계(P1) | 기간·항목별 집계 화면. 서비스 관리자에게는 계속 비노출 |

### B. 기능 중복을 인정한 범위 결정

- **예약·이력·주기 알림**은 기존 제품에도 있다. 새로운 발명이나 유일한 기능이라고 표현하지 않는다.
- **타깃**: 전담 인력이나 CRM 활용이 부족할 가능성이 있는 1~5인 독립 정비소. 문제의 실제 빈도는 인터뷰 전까지 가설이다.
- **업무 흐름**: 전화·현장 예약 → 고객·차량 조회 → 방문·정비 기록 → 재점검 대상 → 연락 준비 → 재예약. 단계별 완성도를 우선한다.
- **데이터 격리**는 비교 우위가 아니라 정비소별 접근 통제라는 필수 설계 원칙이다.
- **고객 앱 미제공**은 차주용 앱과 접점이 다르다는 뜻이지 정비소용 소프트웨어 전체에 대한 독자적 차별점이 아니다.
- **직접 연락의 트레이드오프**: 사장이 대상·문구·시점을 통제하지만 발송과 결과 기록은 수작업으로 남는다.
- **미채택**: 고객 앱·고객 직접 발송·종합 ERP·견적/재고/정산·새 점검 항목·자동 후속 연락을 조사 결과를 이유로 추가하지 않는다. P2·Non-goal은 그대로다.

### C. 사용자 후기에서 얻은 업무 질문 (요약)

후기 8건(R-01~R-08)은 Capterra·Software Advice의 해외 공개 후기 요지 기록이다. **2026-11-24 원문 재확인을 시도했으나 8건 모두 자동 접근이 403으로 거부되어 확인하지 못했다.** 그래서 "검증된 실제 후기"로 표시하지 않고, 사람이 브라우저로 원문을 확인할 때까지 관찰 가설의 근거로만 쓴다(RESEARCH 2.2).
