# 테스트 명세서

> 무엇을 어떤 테스트로 확인하고, 지금 어디까지 실제로 검증됐는지

상태: 작성됨 (2026-11-22 · @하다) — 구현이 진행되면 「상태」 칸을 고친다
근거: 04(T-xx·R-xx 원본), 08(X-xx 원본), 07 6.3(V1 검증 원본), CONVENTIONS 8장, 12 백로그 8·9장

테스트 ID와 기대값의 원본은 04·08이다. 이 문서는 모아 보고 상태를 기록한다. **실행해서 통과를 확인한 것만 "통과"로 적는다.**

## 0. 상태 표기

| 상태 | 뜻 |
|---|---|
| 통과 | CI(또는 기록된 로컬 실행)에서 실제로 실행되어 통과 |
| 실패 | 실행되었고 실패 |
| SKIPPED | 테스트는 있지만 검사 대상이 없어 건너뜀 → **검증 안 됨** |
| 미구현 | 테스트 코드가 아직 없음 |
| 환경상 미검증 | 코드는 있으나 실행 환경이 없어 돌려 보지 못함 |

## 1. 실행 방법

| 종류 | 명령 | 필요한 것 | CI |
|---|---|---|---|
| DB 없는 테스트 (아키텍처·단위: T, R의 Entity 규칙) | `./gradlew build` | JDK 21 | `backend-ci` build |
| DB 테스트 (`@Tag("db")`: 앱 기동·Flyway·통합·X) | `./gradlew dbTest` | MySQL + `DB_*` 환경변수 | `backend-ci` db-test |
| 프론트 | `npm run lint && npm run build` | Node 22 | `frontend-ci` |

CI는 작업 요약에 통과·실패·건너뜀 수를 남기고 리포트를 보관한다.

## 8. 테스트를 쓰는 규칙

- 기능과 테스트를 같은 PR에 넣는다. 테스트 없이 "나중에"로 미루지 않는다(미루면 PR 본문에 미검증으로 적는다).
- 정상 · 오류 · 권한 · 경계 사례를 모두 쓴다.
- 테스트를 통과시키려고 검증·보안·아키텍처 규칙을 끄지 않는다(CONVENTIONS 12장).
- DB가 필요한 테스트에는 `@Tag("db")`를 붙인다.
