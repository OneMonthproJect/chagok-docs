# 차곡 문서·코드 동기화

> 경로 표기: `docs/…`·`CONVENTIONS.md`·`CONTRIBUTING.md`는 `chagok-docs` 기준(코드 레포에서는 `../chagok-docs/…`), `chagok-backend/…`·`chagok-frontend/…`는 각 레포 루트 기준이다(`.claude/rules/ai-rules.md`「작업 폴더와 경로」). 필요한 레포가 작업 폴더에 없으면 지어내지 말고 읽지 못한 것으로 보고한다.

이 프로젝트는 **기획이 기준**이고, 기획은 `chagok-docs`에만 있다. 이 스킬은 세 레포를 함께 읽는다(작업 폴더 `chagok/`). 문서와 코드가 다르면 코드에 맞춰 문서를 슬쩍 고치지 않는다. 어느 쪽이 맞는지는 사람이 정하고, 이 스킬은 영향 범위와 어긋난 곳을 빠짐없이 보여 준다.

## 판단 기준

| 무엇끼리 | 따를 것 |
|---|---|
| 문서 ↔ 코드 | 문서가 기준 (`.claude/rules/ai-rules.md`「AI만의 규칙」) |
| 문서 ↔ 문서 | `.claude/rules/source-of-truth.md`의 판단 순서. 작업 전에 이 파일을 읽는다 |

원본은 그 파일이고 여기서는 가리키기만 한다. claude.ai처럼 파일을 읽을 수 없으면 사용자에게 붙여 달라고 한다. 붙여 주지 않으면 결정 기록(13·닫힌 `결정` 이슈, 늦은 날짜 우선) → 기준 문서 00·04·07·08(각자 자기 영역) → 나머지 문서 순서로 보고, 기준 문서끼리 다르면 고르지 않고 ❓ + `결정` 이슈로 둔다.

## 대응표

| 문서 | 코드·테스트 |
|---|---|
| 00 범위 (P0-핵심/나머지/P1/P2/Non-goal) | 존재하는 기능 전체 (MVP 점검 전 P2, 결정 이슈 없는 P2, Non-goal 기능이 들어와 있으면 안 됨) |
| 04 기능 ID·규칙·T-xx | backend Service, `domain/cycle`, `test/.../cycle` |
| 05 정책 / 06 권한 | backend Service 검증, 보안 설정 |
| 07 테이블·제약·격리 I-xx·시드 | backend `src/main/resources/db/migration/V*.sql`(번호 순서대로 합친 최종 모양), Entity, Repository, `db/seed/demo_seed.sql` |
| 08 API·공통 응답·에러 코드·X-xx | backend Controller, DTO, 에러 코드, `test/.../isolation`, frontend `features/*/api.ts`·`types.ts` |
| 09 화면 S-xx | frontend `src/pages` |
| 10 연결표 | 위 전부 (ID가 바뀌면 10도 고침) |
| 13 changelog · 닫힌 `결정` 이슈 | 기준 문서가 바뀔 때마다 한 줄 (깨지는 상황 칸 포함). 문서끼리 다를 때 가장 먼저 보는 곳 |
| `docs/etc/TEST_테스트명세서.md` | 04 T-xx · 08 X-xx 표와 `test/.../cycle`·`test/.../isolation` |
| `CONVENTIONS.md` 9장 변경 검증표 | 변경이 표보다 많은 곳을 건드리면 구조 문제 신호 |

## 모드 A — 변경 계획 (바꾸기 전에)

사용자가 바꾸려는 것을 받는다(예: "엔진오일 주기 6개월 → 5개월", "API 15 응답에 lastMileage 추가", "reservation에 memo 컬럼").

1. 바꾸려는 것이 관문 1 이후인지 확인한다. 이후에 07·08을 바꾸면 `CONTRIBUTING.md` 7장 순서(`chagok-docs` `결정` 이슈 → `chagok-docs` 문서 PR + 13 changelog → 코드 레포 PR에 문서 PR 링크, 문서 PR 먼저 머지)가 먼저라고 알린다.
2. 대응표를 따라 영향받는 곳을 찾는다. 문서는 해당 절, 코드는 `grep`으로 실제 파일·줄을 찾는다(코드가 아직 없으면 "구현 시 반영"으로 둔다).
3. API가 바뀌면 08 표뿐 아니라 해당 API의 JSON 예시 블록도 영향 범위에 넣는다. 테스트 기대값이 바뀌는지 본다. 주기 규칙 변경은 T-xx 기대값부터 바뀐다.
4. 범위 원칙 위반 여부: 새 기능이면 00의 단계(P2는 MVP 점검 후 결정 이슈), Non-goal, "미리 만들지 않기"에 걸리는지.
5. 건드리는 패키지 수를 CONVENTIONS 9장 표와 비교한다. 더 많으면 "구조가 새는 곳"으로 따로 보고한다.
6. 기능을 빼는(보류) 변경이면 00·04·08에 같은 PR에서 "보류" 표시를 넣도록 영향 범위에 포함한다.
7. 바꾸려는 기준 문서가 다른 기준 문서와 엮이면(예: 08 응답 필드 추가 → 07 컬럼 필요) 양쪽을 모두 영향 범위에 넣는다. 한쪽만 고치면 source-of-truth의 "기준 문서끼리 다름"이 새로 생긴다.

출력:

```markdown
## 변경 요약
무엇을 / 왜 / 관문 1 이후 여부 (→ 결정 이슈 필요)

## 영향 범위
| 구분 | 위치 | 바꿀 내용 |
|---|---|---|
| 문서 | 07 §… | |
| 코드 (backend) | chagok-backend/src/main/java/.../X.java:42 | |
| DB (backend) | 새 마이그레이션 V{n}__….sql (기존 파일 수정 아님) | |
| 테스트 | T-05 기대값 | |
| 프론트 | chagok-frontend/src/features/…/types.ts | |
| 담당 공유 | 프론트 담당, DB관리 | |

## 권장 PR 구성
레포가 나뉘어 있어 문서 PR(chagok-docs)과 코드 PR(레포별)은 항상 따로다. 순서(문서 먼저), 각 PR에 서로 링크할 것, 백·프론트 PR을 같은 날 머지할지

## 13 changelog 초안
| 날짜 | 변경 내용 | 사유 | 영향 (문서·패키지) | 이 결정이 깨지는 상황 | 결정 이슈 |
```

## 모드 B — 대조 점검 (지금 어긋난 곳 찾기)

범위를 받는다(전체 / 특정 문서 / 특정 기능 ID). 문서와 코드를 실제로 읽고 비교한다.

- 07 ↔ Flyway 마이그레이션(V1부터 순서대로 합친 최종 구조): 테이블·컬럼·타입·NOT NULL·UNIQUE·FK·CHECK 값.
- 07 ↔ Entity: 컬럼명, enum 값이 CHECK와 글자까지 같은지.
- 08 ↔ Controller: 메서드·경로·요청 필드·응답 필드·에러 코드. 클래스의 `@RequestMapping`과 메서드 매핑을 합쳐서 비교.
- 08 안: API마다 JSON 예시 블록이 있는지, JSON 문법이 맞는지, 예시의 필드·enum·날짜 형식이 같은 API의 표와 같은지.
- 08 ↔ 프론트 `features/*/types.ts`·`api.ts`: 필드 이름·선택 여부.
- 04 T-xx ↔ `test/.../cycle`, 08 X-xx ↔ `test/.../isolation`: 빠진 테스트 ID.
- 00 ↔ 코드: 차례가 오지 않은 단계(MVP 점검 전 P2 등)·Non-goal 기능이 들어와 있는지, 미리 만든 빈 화면·API·테이블이 있는지.
- 08 "보류" 표시 ↔ 코드: 보류 API가 문서에서만 살아 있거나, 코드에만 남아 있는지.
- 문서 ↔ 문서: 00 범위표 ↔ 04 기능 ID, 04 ↔ 08(기능별 API), 07 ↔ 08(응답 필드가 가리키는 컬럼), 04·07·08 ↔ 09·10의 ID, 13 changelog 결정 ↔ 본문 반영. 어긋나면 source-of-truth 순서로 판단을 적는다.
- CONVENTIONS ↔ 코드: 상태 판정이 cycle 밖에 있는지(`grep -rn "plusMonths\|isBefore\|isAfter" --include=*.java` 결과가 cycle 밖), 다른 도메인 내부 import가 있는지.

출력:

```markdown
## 어긋난 곳
| # | 문서 | 코드 (또는 다른 문서) | 차이 | 어느 쪽을 고칠지 제안 | 근거 (source-of-truth 단계) | 확인 필요 |
|---|---|---|---|---|---|---|

## 빠진 것
- 문서에는 있는데 코드에 없음:
- 코드에는 있는데 문서에 없음:

## 일치 확인
- 확인한 범위와 일치한 항목 수
```

"어느 쪽을 고칠지"는 제안만 한다. 문서 ↔ 코드는 문서 기준, 문서 ↔ 문서는 source-of-truth 순서가 기본값이다. 코드 쪽이 맞아 보이거나 기준 문서끼리 다르면 그 이유를 적고 `결정` 이슈를 권한다.

## 모드 C — API 계약 점검 (08 ↔ 백엔드 ↔ 프론트)

모드 B의 08 부분만 떼어 빠르게 돈다. 프론트·백엔드가 처음 연결될 때, 기능 묶음이 끝났을 때, 릴리스 점검 전에 쓴다. **코드와 문서를 고치지 않고 보고만 한다.**

| 쪽 | 볼 곳 |
|---|---|
| 계약 (원본) | 08의 API 번호·메서드·경로·요청·응답 표와 JSON 예시 블록, 에러 코드, 공통 응답 모양 |
| 백엔드 | Controller 매핑(클래스 `@RequestMapping` + 메서드), 요청·응답 DTO, `ErrorCode`, `GlobalExceptionHandler` |
| 프론트 | `features/*/api.ts`의 호출 경로·메서드·보내는 필드, `features/*/types.ts`, 화면이 읽는 응답 필드 |

- 범위가 넓으면 하위 에이전트 둘로 나눠 읽는다(백엔드 쪽 · 프론트 쪽). 둘의 결과를 08 기준으로 합친다.
- 의심 항목만 실제 요청(curl)으로 재현한다. 앱을 띄우거나 요청을 보내기 전에 한 줄로 알린다. 시드 계정을 쓴다.
- 먼저 08 안에서 표와 JSON 예시가 서로 같은지 본다. 08끼리 다르면 코드 비교 전에 ❓로 보고한다.
- 확인 항목: 경로·메서드, 필드 이름(camelCase 오타)·타입·필수 여부, enum 값(정비 구분·예약 상태·항목 상태), 날짜 형식, 에러 코드·상태 코드(401/403/404/409), 공통 응답 감싸기, 08 「보류」 API가 코드에 남았는지, 코드에만 있는 API.

출력:

```markdown
## API 계약 점검 (범위: 전체 / API n~m / F-xxx)

| API | 항목 | 08 (표 / JSON 예시) | 백엔드 | 프론트 | 판정 |
|---|---|---|---|---|---|
| 15 GET /api/targets | 응답 필드 | nextDueDate | nextDueDate | nextDate | ❌ 프론트 |

판정: ✅ 일치 · ❌ 불일치(고칠 쪽) · ❓ 08이 모호함

## 요약
- ❌ n건: 코드를 고칠 것 n / 08을 고칠 것 n (→ 결정 이슈 필요 여부)
- curl로 재현한 것:
- 프론트 담당에게 공유할 것: (CONTRIBUTING 7장: 08이 바뀌면 PR 링크 공유)

## AI 사용 기록 (chagok-docs `docs/etc/AI_USAGE_AI활용기록.md`에 추가할 줄)
| 날짜 | 레포#이슈 | chagok-spec-sync 모드 C | API 계약 점검 n건 | 사람이 바꾼 것: (사람이 채움) |
```

기본값은 08 기준이다. 08이 모호하거나 코드 쪽이 맞아 보이면 ❓로 두고 모드 A로 넘긴다.
